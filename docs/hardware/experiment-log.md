## EXP-001: 連続streamingの実効sample rate

- **日時**: 2026-08-17（初回測定）、**2026-08-18（治具を直して取り直し）**。いずれもJST
- **目的**: `HW-TBD-034`の未解決3点のうち、(2)「SRAM 2 KBに対する取得方式」と
  (1)「基準電圧の校正」の測定側を解く。**連続streamingで何Sample/s出るかを実測し**、
  `Sample rateとlog形式`の必須要件と突き合わせる。あわせてAV<sub>CC</sub>基準での
  内蔵1.1 V基準の生ADC値を採る
- **仮説**:
  1. 連続streamingは`Sample rateとlog形式`の必須要件を2 channel同時で満たす（**要件値はここへ再掲しない**）
  2. `DS40002061B` Table 24-1 の`Auto Triggered conversions`は13.5 cyclesであり、
     ADC clock 125 kHzでは合計約9.26 kSample/sになる
  3. free running modeでISRから`ADMUX`を書くと、§24.5.1により結果のchannel帰属が
     1変換ぶん遅れる。したがって素朴に現在の`ADMUX`でtagを付けるとlabelが入れ替わる
- **ハードウェア構成**:
  - 測定器: Arduino Uno R3（`MEAS-02`。`BOARD MODEL UNO R3`／`ATMEGA328P-PU`／`MEGA16U2`）
  - USB idは`2341:0043`（Arduino SA, Uno R3 CDC ACM）として認識。**serial番号は記録しない**
  - **DeskCat側へは一切接続していない。**Arduino単体とPCだけで完結する
  - 開発端末: 実機のLinux（Ubuntu 24.04.4、kernel 7.0.0-28-generic、x86_64、
    `systemd-detect-virt: none`）。ADR-0005の要求を満たす
- **回路 revision**: 配線は治具のみ。`A0` → Arduinoの`3V3` pin、`A1` → Arduinoの`GND`。
  **抵抗を入れていない。**分圧も外部電源も使っていない。
  2 channelへ意図的に異なる電圧を入れて、channel帰属の入れ替わりを検出できる形にした
- **firmware commit**: 治具は`hardware/measurement/`配下にある。初回測定時はrepository commit `3a34aef`、
  取り直し時は同じbranchのreview指摘修正後（`測定治具のreview指摘4件を直す`）である
- **電源条件**: ArduinoはPCのUSBからのみ給電。`VUSBMax` 5.5 V。監視対象への通電は行っていない。
  **DeskCat側のrailを通らないことの裏付けは、公式Power Treeのblock図の粒度までである**
  （`手持ち候補の現物識別`）。**schematic粒度での一致は未確認であり、独立給電は候補条件のままである。**
  この実験はそれを前進させていない
- **設定**:
  - 治具: `hardware/measurement/arduino-transient-logger`（連続streaming）と
    `hardware/measurement/arduino-vref-calibrate`（基準電圧）
  - 集計: `hardware/measurement/adc_stream_rate.py`（Python 3標準ライブラリのみ）
  - toolchain: `arduino-cli` 1.5.1（公式releaseのtarballをsha256照合して導入）、
    `arduino:avr` 1.8.8、`avr-gcc` 7.3.0-atmel3.6.1-arduino7、`avrdude` 8.0.0-arduino1
  - ADC基準はAV<sub>CC</sub>（`REFS1:0 = 01`。`DS40002061B` Table 24-3）
  - 取得方式は**連続streaming**。burst captureではない
  - `dialout` group追加後、再loginしていないため全serial操作を`sg dialout -c '...'`で実行
  - **周囲温度: 未測定。**温度計を用意していなかった。**内蔵基準は温度で動くため、
    基準電圧側の値は温度条件を伴わない測定である**（作業1のsample rateは温度条件を要さない）
- **手順**:
  1. board無しで parser の自己testを通す（`test_adc_stream_rate.py`、22 case）
  2. sketchをcompileし、`arduino-cli compile --upload`でuploadする
  3. 各条件でstreamingを受け、届いたsample数・取りこぼし・block欠番を数える
     （初回測定は8〜10秒、取り直しは各条件10秒。採用区間は9.85〜9.97秒、受信blockは750〜1502件）
  4. 起動直後の4 blockを捨てる（過渡を除くため。捨てた数も報告させる）
  5. channel別の生ADC値の大小関係が、手順で入れた既知電圧と一致するか確認する
  6. 基準電圧側は単発変換で`GND`／`VBG`／`A0`／`A1`を読み、切替直後の生値も並べて記録する

### 観測結果

1. **必須要件は2 channel同時で満たした。**最も遅い条件でも1 channelあたり2689.7 Sample/sである。
   ただしその条件（baud 115200）は取りこぼしを41851件出しており、**rateを満たすことと
   取りこぼしが無いことは別である。**
2. **baud 115200はtransportが律速している。**1 blockはheader 24 B + payload 256 Bで
   128 sampleを運ぶため1 sampleあたり**2.1875 B**である。
   **ここで公称baudを使うと計算が実測より低く出る。**`DS40002061B` Table 20-7 は
   f<sub>osc</sub> 16 MHz・U2X=1・115.2 kbps の`UBRRn`を**16**、**Error を +2.1 %**としており、
   実baudは約117.6 kbpsになる。8N1では1 byteに10 bitを要するので約11765 B/sであり、
   **2.1875 Bで割ると約5378 Sample/sとなる。実測5379.3はこれと0.02 %で一致する。**
   なお500000と1000000は同表で Error 0.0 % であり、この効果は出ない
   （どちらもADC側が律速し、取りこぼしは0になった）。
3. **取得rateはchannel数に依存しなかった。**1 chと2 chで合計取得rateが同じ値になり、
   1 channelあたりのrateは合計をchannel数で割った値と一致した。
4. **仮説2は外れた。**取得rateは全条件で`ADC clock / 13`と一致した
   （125000 / 13 = 9615.38に対し実測9615.4、250000 / 13 = 19230.77に対し実測19230.8）。
   Table 24-1が`Auto Triggered conversions`に与える13.5 cyclesとは一致しない。
   **この差の機序はこの測定では確定していない。**実測値を採り、差がある事実を記録する。
5. **仮説3は当たった。**§24.5.1の1変換遅れを織り込んだchannel帰属で、
   全条件で`ch0 > ch1`（673 対 0）となり、入れた既知電圧の大小関係と一致した。
   **段数を誤ると値は正常に見えたままlabelだけが入れ替わるため、
   異なる既知電圧を入れることがこの確認の前提である。**
6. **`DS40002061B` §24.4の「bandgapは安定するまで最初の値が誤りうる」が実測で見えた。**
   `VBG`へ切り替えた直後の1変換だけが126〜161とばらつき、以降は226で安定した。
   **ただしこれは4 traceの観測であり、しかも周囲温度を記録していない1条件下のものである。**
   **「捨てるのは1変換で足りる」と一般化しない。**AV<sub>CC</sub>・温度・channel切り替えの
   条件が変われば必要数が変わりうる。**手順は`CAL_DISCARD=8`を維持する**（余裕を持たせた値であり、
   1変換で足りたのはこのrunに限った観測である）。
7. **ADC offsetは現分解能では検出されなかった。**内部の`0V (GND)`（MUX `1111`）と、
   `GND`へ配線した`A1`がいずれも0を返した。
8. `A0`のmin/max幅は125 kHzでも250 kHzでも4 LSB（672〜676）に収まり、
   **この測定では両者の差を分離できなかった。**§24.4 は250 kHzが最大分解能の規定外である
   と述べているが、**その影響をこの観測で定量してはいない。**
9. **transportは常に無損失とは言えない。**2026-08-18の1回目の取り直しでは、7条件のうち2条件で
   予約bitの破れを1件検出し、その block を読み捨てた結果 block欠番が1件出た
   （約750〜1500 blockに対し1件）。**parserが検出して読み捨て、収支もその欠落を正しく説明した。**
   **`dropped`を32 bitへ広げた後の取り直しでは、7条件すべてで0件だった。**
   したがって**発生率は低いが0とは言えない**。取りこぼし（ISRがringに入れられなかった件数）とは
   別の事象である。
10. **壁時計基準と Arduino 時計基準の rate が 0.1 % 以内で一致した。**
   初回測定でこの2つに約0.5 %の差があったのは測定系の集計の誤りであり、下記`訂正`のとおりである。

### 訂正（2026-08-18）

**初回測定で記録した値には、測定系の集計に起因する誤りがあった。**
[PR #145](https://github.com/wachi-yoshitaka-11-dev/deskcat/pull/145)の自動reviewの指摘を
2巡受けて確認し、**いずれも妥当であったため治具を直して同じ条件を取り直した。**
上の`raw data`は最後に取り直した値である。**wire formatが変わった回では全条件を再測定している。**

| 何が誤っていたか | 影響 | 直し方 |
|---|---|---|
| 壁時計rateの分子と分母が同じ区間でなかった（捨てたblockの時間が分母に残っていた） | **実効rateが約0.5 %低く出ていた。**壁時計と`micros()`の差を「window端の副作用」と誤って説明していた | 分子・分母をともにblock受信時刻の区間へ揃えた |
| ADC変換式の分母に1023を使っていた | 校正比が約0.098 %ずれていた | §24.7 の `ADC = (V_IN × 1024) / V_REF` に従い1024へ直した |
| `taken`がring滞留分を含むことを収支から差し引いていなかった | 正常な測定に対して「不整合」を誤報しうる状態だった（実測では誤報は出ていない） | headerへ`pending`を追加して差し引いた |
| CSVの時刻indexを単調加算だけで進めていた | 回線上でblockを失うと以降の時刻ずれが累積した。**上記9のとおりこの欠落は実際に起きるため、実害のある誤りだった** | blockごとに`taken - pending`から引き直し、`lost_blocks`もguardへ入れた |
| **`dropped`をwire formatで16 bitにしていた** | **baud 115200では10秒で41851件に達するため約16秒でwrapする。**境界では差が0に見え、**CSVのguardを誤って通す** | 32 bitへ広げた（header 22 B → 24 B）。parser・README・testも揃え、桁落ちしないことをtestで固定した |
| **`micros()`のwrapを跨ぐ取得を弾いていなかった** | 約4295秒を超えると`us_delta()`が残余しか返さず、Arduino時計基準のrateとCSVの時刻が誤りになる | `--seconds`を4000未満に制限し、wrapしないPCの単調時計で判定してrateとCSVを抑止した |
| **`Arduino Uno`行に「通電はしていない」が残っていた** | 同じ文書の`MEAS-02`行が初回通電を記録しており、現況が2箇所で食い違っていた | 初回通電の事実へ揃えた |
| **手順に記録したtest件数が古かった** | 実体と合っていなかった | 実数へ揃えた |

**結論は変わっていない。**1 channelあたりの実測値は125 kHzで4808.9 Sample/sとなり、
**依然として目標帯には届かない。**取得rateが`ADC clock / 13`と一致することも変わらない。

**この実験の結論は変わらない。**

### 結論

- **仮説1: supported。**連続streamingは必須要件を2 channel同時で満たす。
  **burst captureを採らずに済み、SRAM 2 KBの制約は取得方式の障害にならない。**
- **仮説2: rejected。**上記4のとおり実測は`ADC clock / 13`だった。
- **仮説3: supported。**上記5のとおり。
- **作業2の合格条件は満たしていない。**「換算係数と手順が別の人が同じ結果を再現できる形で
  残っていること」に対し、**周囲温度を記録しておらず**、`DS40002061B`はこの品の内蔵基準の

  `Calibrated Bandgap Voltage vs. V`<sub>`CC`</sub>（Figure 31-365）が示すとおり
  **内蔵基準はV<sub>CC</sub>にも依存するため、あるAV<sub>CC</sub>で求めた値を

  **デジタルテスター（DT830B）による5 V pinの実測と、テスター自身の確度が未取得であり、
  校正の不確かさは`TBD`である。**確度を超える主張をしない。
- **`HW-TBD-034`はcloseしない。**解いたのは未解決3点のうち(2)と、(1)の測定側だけである。
  (3)「GND topologyへの影響」は未着手であり、**DeskCat側への接続と通電を伴うため
  人間の立ち会いが要る。**
- **`MEAS-02`の採否は未確定である。**方式1の採用は決定済みだが、この品で足りるかは
  (1)と(3)が解けるまで判定しない。
- **未観測区間について新たな主張をしない。**正本（`ESP32自身のADCは測定対象から独立していない`）は
  未観測区間を3種に分け、**独立した記録係で塞げるのは`brownout／reset中`と`capture window外`の2種だけで、
  `sample間`は残る**と定めている。この実験が示したのは**`capture window外`を塞ぐ取得方式が成立する**ことまでである。
  **`brownout／reset中`は塞げていない。**独立給電がまだ候補条件であり（schematic粒度が未確認）、
  監視対象へ通電もしていない。**`sample間`は方式によらず残る。**
  **（2026-08-22の追記）`EXP-003`で監視対象のESP32へ接続して測定した。**
  **ただし`EXP-003`は静的な条件比較であり過渡を測っていないため、`brownout／reset中`を塞げていないという結論は変わらない。**

### raw data

**`A1`が浮いていたときの記録も残す。**配線前、`A1`をどこにも繋いでいない状態では
**試行1** `n=64 min=438 max=483 mean=454.2`／**試行2** `n=64 min=478 max=832 mean=686.4`／**試行3** `n=64 min=346 max=770 mean=545.4` と

### 観測結果

1. **ADCの読みは既知電圧と一致した。**AV<sub>CC</sub>の代理値5.04 Vを使うと、

2. **GNDを直結すると`A0`が +0.42 LSB（約 +2.1 mV）上がった。**
   条件内のばらつき（Aが0.156 LSB、Bが0.219 LSB）より大きく、**1 LSB（4.92 mV）より小さい。**
   平均を採って初めて見える大きさである。**（2026-08-22の追記）`EXP-004`でGND offsetを両極性で測った結果、この差はGND offsetの変化（+2.7 mV）で説明できることが分かった。差は0.62 mVで条件内のばらつき以内である。**
3. **この差はDT830Bでは裁定できない。**+2.08 mVは20 Vrangeの最小単位の約1/4.8であり、
   **ADCの方が分解能が高い。**テスターでは差の存在を確認も否定もできない。
4. **`A1`は両条件でmin=max=0だった。****これが示すのは片側だけである。**ADCは単端であり負電圧を測れないため、
   **`0`は「ESP32の`GND`がArduinoの`GND`より1 LSB以上高くはない」ことしか意味しない。**
   **ESP32の`GND`が低い側にずれている場合、入力は測定範囲の外であり、保護構造の影響で同じく`0`と観測されうる。**
   **その状態はADCが保証する測定範囲ではないため、`0`から差の絶対値を結論できない。**
   **（2026-08-22の追記）`EXP-004`で両極性を測った。ESP32の`GND`はArduinoの`GND`より低く、条件Aで−6.5 mV、条件Bで−3.8 mVだった。**
   **1 LSB（4.92 mV）より大きいoffsetが、まさにADCの死角にあった。**
   **したがってGNDの確認は片側（正方向のみ）であり、両極性を測れる手段を用意するまで完了しない**
   （[PR #160](https://github.com/wachi-yoshitaka-11-dev/deskcat/pull/160)の自動reviewの指摘）。
5. **`VBG`は条件間でほぼ動かなかった**（−0.09 LSB）。基準側が変わっていないため、
   `A0`の変化は入力側の変化である。
6. **入力headroomは 0.22 V（AV<sub>CC</sub>の4.4 %）しかない。**
   ADCのfull scaleがAV<sub>CC</sub>の5.04 Vで、ESP32の5 V railが4.82 Vである。
   **各読みの最小単位が10 mVなので、差の不確かさは少なくとも ±20 mV。**
   **したがってheadroomは少なくとも 0.20〜0.24 V の範囲にある**（確度が未取得なので実際はこれより広い）。
7. **抜き差しで条件が壊れていないことを確認した。**`A0`のジャンパを`3V3`から抜いて電圧を測り、
   戻したあとの`A0`は条件Bとの差が **−0.08 LSB（−0.4 mV）**で、条件内のばらつきより小さい。
   **入力電流は測定していない。**確認できたのは**この条件でジャンパを抜き差ししてもrailの変化を観測しなかった**ことである。**「ADCの入力は電流を流さない」とは書かない**（[PR #160](https://github.com/wachi-yoshitaka-11-dev/deskcat/pull/160)の自動reviewの指摘）。
8. **異常は無かった。**異音、発熱、ESP32のresetやbrownout、ADC値の異常のいずれも観測されなかった。
   **GNDを直結した瞬間にも変化は無かった。**

### この記録が主張しないこと

- **段階Cのtopologyの検証ではない。**star point構成は`5V ingress GND`を含み、
  それを作る変換基板`PSU-INGRESS-01`は未購入である。**したがって(3)は完了していない。**
- **`5V ingress GND`とstar pointの同一node性、servo戻りとshuntを含むstar point、
  `ADC-SHUNT`の基準電位はいずれも確認していない。**shuntもservoも接続していない。
- **観測項目2の差の原因を特定していない。**GNDの直結が何を変えたかは説明していない。
- **`HW-TBD-028`の合否判定には使っていない。**判定は`Blocked`のままである。
  ESP32の`5V`が4.82 Vだったことも、**判定値との照合には使わない**
  （DT830Bの確度が未取得であり、`DT830Bを電流測定に使うときの制約`と同じ理由で
  読みだけでgateを通さない）。
- **過渡を測っていない。**これは静的な条件比較であり、起動時の電源過渡の観測ではない。

### 結論

- **段階B-1で確認できる3項目はすべて実測できた。**ADC値の妥当性、GNDの結合の影響、入力headroomである。
- **入力headroomが0.22 Vしかないことは、dividerを外せないことの定量的な根拠である。**
  `power-budget.md`の`5 V railをADCへ直結する条件`はdividerを既定として残していたが、
  **これまで理由は定性的だった。**5 V railが220 mVを超えて跳ねればfull scaleを超えて飽和し、
  **その区間の波形が失われる。**起動時の過渡を追う用途に対して、上に4.4 %の余裕は足りない。
- **(3) GND topologyへの影響は、段階B-1で実測はできたが解けていない。**理由が2つある。
  **(i) GNDの確認が片側だけである**（上の観測4。単端ADCの`0`は正方向しか縛らない）。
  **(ii) star point構成そのものの確認が残り、それは変換基板が揃うまでできない。**
  **したがって段階B-1を実施しても、この項目は未解決である。**

## EXP-004: GND offsetを両極性で測る

**目的**: `EXP-003`が単端ADCでは片側しか縛れなかったGNDの電位差を、極性を読める手段で測る。
`HW-TBD-034`作業3の(3)の残作業である。

**実施日**: 2026-08-22（**JST**。[CONTRIBUTING.md](https://github.com/wachi-yoshitaka-11-dev/deskcat/blob/main/CONTRIBUTING.md)が`日付はJST（UTC+9）で判断する`と定めている。**UTCでは前日になる**）。実機Linux。**人間が基板のそばで観察している状態で行った。**
**構成は`EXP-003`と同じ**（Arduino Uno R3とESP32 DevKitCをともにPCのUSBで給電。servoも外部電源も接続していない）。

### 測定手段

**DT830Bの`V⎓`の`200m`レンジ**（最小単位0.1 mV。`MEAS-03`）。
**このレンジを選んだ理由は2つある。**

1. **極性を読める。**負の入力に対して`−`を表示する（取扱説明書の`ディスプレイ`の節）。
   **単端ADCは負電圧を測れないため、この点が決定的である。**
2. **最小単位が0.1 mVで、ADCの1 LSB（4.92 mV）より約49倍細かい。**

赤プローブをESP32の`GND`、黒プローブをArduinoの`GND`へ当てた。
**したがって読みは`V(ESP32 GND) − V(Arduino GND)`である。**

### raw data

| 条件 | GNDの結合 | 読み |
|---|---|---|
| A | 直結なし（PC経由でのみ共通） | **−6.5 mV** |
| B | `Arduino GND`と`ESP32 GND`を1本で直結 | **−3.8 mV** |

### 観測結果

1. **ESP32の`GND`はArduinoの`GND`より低い。**両条件で符号が負である。
   **これは`EXP-003`の単端ADCが構造的に観測できない側である。**
2. **offsetはADCの1 LSBより大きい。**条件Aの6.5 mVは1 LSB（4.92 mV）を超える。
   **したがって`EXP-003`で`A1`が`min=max=0`だったのは、offsetが小さかったからではない。**
   **測れる大きさのoffsetが、ADCの死角にあったからである。**
   [PR #160](https://github.com/wachi-yoshitaka-11-dev/deskcat/pull/160)の自動reviewの指摘は仮定ではなく、実際にこうなっていた。
3. **`GND`の直結はoffsetを消さない。**−6.5 mVから−3.8 mVへ縮むが**残る。**
4. **`EXP-003`の`A0`の差の原因が説明できる。**`A0`はArduinoの`GND`基準でESP32の`3V3`を測るため、
   **GND offsetがそのまま乗る。**offsetが+2.7 mV変化したことに対し、
   **ADCが見た`A0`の差は+2.08 mVだった。差は0.62 mVで、`EXP-003`の条件内のばらつき（1.1 mV）以内である。**
   **2つの独立した測定手段が整合している。**
   `EXP-003`の観測2で「原因は特定していない」としていたが、**この説明で整合する。**
5. **GND offsetを入れるとADC値の妥当性の一致が良くなる。**
   DT830BはESP32の`GND`基準で`3V3`を3.34 Vと読んだ。Arduinoの`GND`基準へ換算すると
   条件Aは3.3335 V、条件Bは3.3362 Vになる。**ADCの実測は3.3333 Vと3.3354 Vで、
   差は−0.16 mVと−0.78 mVである。**
   **offsetを入れる前の差（−6.7 mVと−4.6 mV）より1桁小さい。**

### この記録が主張しないこと

- **offsetの原因を特定していない。**PCの内部でGNDが共通化される経路の抵抗、
  USB cableの抵抗、両boardの消費電流のいずれが効いているかは調べていない。
- **（2026-08-22の追記）このレンジには0.2 mVのゼロ点オフセットがある**（`EXP-005`のゼロ点確認）。**上の絶対値はその系統誤差を持つ。**
  **ただし2条件の差は影響を受けない**（定数オフセットは引き算で消える）。**したがってADCが見た差と整合するという結論は変わらない。**
- **DT830Bの確度は未取得である。**上の値は最小単位0.1 mVの読みであり、
  **確度を超える主張はしない**（正は`DT830Bの一次資料で分かったこと（2026-08-21）`）。
  **確度が未取得であるため、6.5 mVという値そのものの不確かさは`TBD`である。**
- **`HW-TBD-028`の合否判定には使っていない。**判定は`Blocked`のままである。
- **これは静的な測定である。**過渡中のoffsetの振る舞いは測っていない。
  **起動時にoffsetがどう動くかは分からない。**
- **段階Cのtopologyの検証ではない。**star point構成は変換基板`PSU-INGRESS-01`が揃うまで組めない。

### 結論

- **(3)のうち「GNDの確認が片側だけである」という不足は解消した。**両極性で測り、符号と大きさを得た。
- **それでも(3)は完了しない。**star point構成そのものの確認が残る。
- **設計に効く事実が1つ出た。`GND`の直結はoffsetを消さない。**
  数mVのoffsetは`HW-TBD-028`の絶対電圧の判定値に対して余裕の少ないところで効く。
  **star pointの設計は、直結すればoffsetが消えるという前提で行えない。**

## EXP-005: `5V` pinと`AVCC` pinの差の上限

**目的**: `EXP-002`が`AVCC`の代理として測った`5V` pinと、実際の`AVCC` pinの差を縛る。
`HW-TBD-034`の未解決3点のうち(1)の残作業である。

**実施日**: 2026-08-22（**JST**）。実機Linux。**人間が基板のそばで観察している状態で行った。**
**Arduino Uno R3のUSB給電のみ。servoも外部電源も接続していない。**

### 測る場所を一次資料で決めた

`AVCC`は`+5V`から`L2`（10 µH）を経てpin 20へ至る（`5V` pinと`AVCC` pinの差（2026-08-22の調査））。
**`L2`は`0805`（2.0 × 1.25 mm）で、DT830Bのプローブでは当てられなかった。**

**代わりにpin 20を直接測った。**ATmega328Pはsocket実装（`DIL28-3`）でpin間隔が2.54 mmあり、
`0805`のパッドより当てやすい。位置はArduino公式のboard reference designから求めた。

| 項目 | 値 |
|---|---|
| 出典 | `UNO-TH_Rev3e.brd`（<https://content.arduino.cc/assets/UNO-TH_Rev3e.zip>。sha256 `680cba4a0e6fb3a42ebc0d7055a1c924baabc19ebfd328e8da4454fa8fed7145`） |
| `L2` | `package="0805" value="10uH" x="39.116" y="8.128"`。**メーカー品番は無い**（`library="Induttanze"`） |
| pin 20（`AVCC`） | `x=42.545 y=12.573`（`ZU4`が`x=46.355 y=16.383`、`rot="R180"`の`DIL28-3`から算出） |
| 座標系 | 基板外形は68.58 × 53.34 mm。**原点は写真で見たときの左下**（DC jackが`x=5.334 y=8.382`、USBが`y=38.100`であることから決めた） |
| 目印 | `POWER`ヘッダの列（`y=2.540`）から上へ10.0 mm、`5V` pin（`x=38.100`）から右へ4.4 mm |

**pin 22は`GND`である。**`AVCC`と`GND`を短絡させると`L2`と5 V系に電流が流れるため、
**pin 19／21／22へ同時に触れない**ことを条件にした。

### raw data

DT830Bの`V⎓`の`200m`レンジ（最小単位0.1 mV）。赤プローブは`5V` pinへ中継したジャンパへ固定し、
黒プローブだけを動かした。

| 測定 | 表示 |
|---|---|
| `5V` pin → pin 20（`AVCC`） | **`00.2`** |
| **ゼロ点確認**（両プローブを同一点へ当てる） | **`00.2`** |

**2つの表示は同一である。**どちらも`XX.X`形式で0.2 mVと読める
（同レンジで測った`EXP-004`の`-06.5`も同じ形式である）。

**これはゼロ法（null測定）である。**測定対象を入れても表示が動かなかったため、
**差はこのレンジの分解能を動かせていない。**

**この読み方が置いている前提を明示する。**
**(a) 表示の丸めが2回の測定で同じように働き、ヒステリシスが無いこと。**取扱説明書にこの点の記載は無く、**確かめていない。**
**(b) 表示が安定していたこと。****記録していない。**ふらついていた場合、「同じ表示」の意味は弱まる。**次に同種の測定を行うときは、安定かふらつきかを記録する。**

### 観測結果

1. **このレンジには0.2 mVのゼロ点オフセットがある。**両プローブを同一点へ当てて`00.2`が出た。
   理屈上そこは0 Vであるため、**表示はテスター自身のオフセットである。**
2. **`5V` pinとpin 20の差は、このレンジの分解能未満である。**
   ゼロ点と測定値が**同じ表示**であったため、**差は表示を1 count動かすには足りなかった。**
   1 countは0.1 mVである。**したがって差の上限は0.1 mVである。**
   **差の値そのものは得られていない。**0でも0.09 mVでも同じ表示になる。
   **上限だけが言える。**
3. **この上限は、`EXP-002`が既に記録している不確かさに埋もれる。**2つの量と比べる。
   **(a) `AVCC`実測そのものの分解能は10 mV**（20 Vレンジの最小単位）で、**0.1 mVはその100分の1**である。
   **(b) `V_INT`へ伝わった合成の不確かさは少なくとも ±0.003 V**で、
   **0.1 mVが`V_INT`へ与える影響は約0.02 mV**（比率0.2206を掛ける）であり、**その130分の1以下**である。
   **どちらと比べても支配項にならない。**

### この記録が主張しないこと

- **差の値を測ってはいない。上限を与えただけである。**0.1 mVより細かい分解能はこの計器に無い。**ゼロ法で上限を与えただけである。**
- **`L2`のDCRは未取得のままである。**board fileにもメーカー品番が無い。
  **差を`I_AVCC × DCR`から算出したのではなく、直接測って上限を与えた。**
- **ゼロ点オフセットの原因を特定していない。**
- **表示が安定していたかを記録していない。**上の前提(b)のとおりである。
- **表示の丸めの挙動を確かめていない。**上の前提(a)のとおりである。**したがって上限0.1 mVは、その2つの前提のもとでの値である。**
- **確度は未取得である**（正は`DT830Bの一次資料で分かったこと（2026-08-21）`）。
  **上限0.1 mVは最小単位からの値であり、確度を超える主張はしない。**
- **`HW-TBD-028`の合否判定には使っていない。**判定は`Blocked`のままである。

### `EXP-004`への影響

**同じゼロ点オフセットは`EXP-004`のGND offsetの読みにも乗っている。**

- **絶対値**（条件Aと条件Bの読み）は**0.2 mVの系統誤差を持つ。**
- **2条件の差は影響を受けない。**定数オフセットは引き算で消える。
  **したがって「ADCが見た差と整合する」という`EXP-004`の結論は変わらない。**

### 結論

**(1) 基準電圧の校正は解けた。**

代理値の限定が実質的に解消した。**`5V` pinと`AVCC` pinの差は0.1 mV未満であり、
`V_INT`へ与える影響は約0.02 mV、`EXP-002`が既に記録している不確かさ
（少なくとも ±0.003 V）の130分の1以下である。**
したがって`EXP-002`の`V_INT`を、**その不確かさの範囲で絶対値として扱える。**

**それでも`HW-TBD-034`はcloseしない。**(3)のstar point構成の確認が残り、
close条件は3点だけではない。

## EXP-007: journal永続化と直後のPi再起動

**目的**: [#247](https://github.com/wachi-yoshitaka-11-dev/deskcat/issues/247)のPM決定（2026-08-29）に従い、`journalctl`の`Storage`を`persistent`化し（`SystemMaxUse=32M`上限付き）、kernelログが再起動をまたいで残る状態にする。その直後にPiが実際に再起動した事象を記録する。

**実施日**: 2026-08-29（JST）。Raspberry Pi Runtime実機（`deskcat-pi`）とDocs/Review端末（ssh経由）。sudo操作はユーザーの承認を得て実施した。

### journal永続化の実施

- `/etc/systemd/journald.conf.d/50-persistent-storage.conf`に`Storage=persistent`／`SystemMaxUse=32M`を追加し、`systemd-journald`を再起動
- `/var/log/journal/`に実file（`system.journal`／`user-1000.journal`）ができたことを確認した

### 再起動事象

**何をしていたか**: 測定計画6節の残り2項目のうち「Pi単体でのbuild負荷比較」を実施しようとしていた。検証済みでない条件（`cargo build --release`）で建て直し、さらにその完了確認中に**別の検証済みコマンドのbuildをもう一度重ねて起動してしまい、空きメモリ68MiBの状態で2つのcargo buildが同時に動く状態を作った（AI側の判断ミス）。**二重buildを解消しようとssh経由で`kill`コマンドを送った直後、Piがネットワークから応答しなくなった。

タイムライン（`journalctl`と`boot_id`による再構成、時刻はJST）:

| 時刻 | 内容 |
|---|---|
| 02:47頃 | `--release`buildが依然として稼働中（見落とし）に、debug buildをさらに起動。空きメモリ68MiB |
| 02:48:29–02:48:35 | 二重build解消のための`kill`コマンドがssh接続。正常に切断（`disconnected by user`） |
| 02:48:35 | rail loggerのCSVの最後の行。以降、記録が途切れる（`# session end`行が無い＝正常終了ではない） |
| 02:48:41 | 新しい`boot_id`（`85d4479e…`）でkernelログが開始。旧bootとの間はわずか6秒 |
| 02:48:41 | journal再起動時、旧journalファイルが「corrupted or uncleanly shut down」として作り直された（正常なshutdownでは起きない） |
| 02:59頃 | ping応答が復帰。人間が物理的に立ち会っており、その時点でLEDは点灯、DT830B読みは5.30V（プローブを固定した状態） |

### 追加の観測

- **`throttled`の低電圧sticky bitは、新bootで`0x0`**（このboot中は低電圧未検出）。旧boot終了直前の最後のポーリング行（02:48:35時点）も`throttled=0x0`だった
- **新bootのfilesystemは`orphan cleanup`のみでEXT4エラー無し**

### この記録が主張しないこと

- **原因を確定していない。**証拠は「AI側の二重build（メモリ逼迫）が引き金」という仮説を、タイミングの近さから支持するが、旧bootのkernelログにOOM killerの記録が一つも無いため断定できない
- **物理的な短絡が引き金だった可能性を完全には排除できない。**ただしタイムラインは、後で報告された「プローブを外したらLEDが消え、その後点滅した」という観察より前に再起動が始まっていたことを示しており、それが新たな短絡ではなく既に始まっていた同じ再起動の起動シーケンス（SDカードアクセスによる点滅）だった可能性を示唆する
- **1秒間隔のポーリングでは、間隔未満の瞬間的な電圧降下は検出できない。**`throttled=0x0`の記録は、この限界の範囲内でのものである
- `docs/hardware/`の値は変更していない。案Aの再試験は行っていない

### 是正

- 今後、Pi上のcargo buildはAGENTS.md検証済みコマンドのみを使い、同時に2つ以上走らせない。`--release`など未検証条件は使わない
- DT830Bのプローブは、GPIO pinへ手持ちで当てず、線を延長して固定する（本事象後に対応済み）

### 結論

**Piは実際に再起動した（`boot_id`変化で確定）。**原因は特定できていない。journal永続化は意図通り機能し、この事象が期せずして`journalctl -b -1`が使えることの実地確認になった（`EXP-006`参照）。

## EXP-008: 段階B-1でのPi単体build負荷比較とESP32側基準値

### 段2: 分圧

5. **低下はbuild開始の1秒以内に現れ、終了の直後に戻った。**最深は+1秒の−18.6 mV、回復は+14秒から始まり+16秒で基準へ戻る。**`BUILD_START`／`BUILD_END`と一致する。**
6. **この低下はAV<sub>CC</sub>の変動ではない。**対照のch1（Arduinoの`3V3`）は3区間で 673.564／673.558／673.565 であり、**差は0.006 counts しかない。**
7. **数の裏付け。**各区間6.6万サンプル、標準偏差1 count前後であり、平均の標準誤差は0.03 mVに満たない。**14.8 mVはその桁を大きく超える。**
8. **build中はばらつきも増えた。**標準偏差が0.929→1.355 counts（rail換算6.1→8.9 mV）へ上がる。
9. **2つの時間軸が突き合わせられた。**Arduino側CSVの壁時計anchorと、Pi側polling logのISO8601が同じ窓を指している（`volts_core`の1.2000V→1.3500V、温度上昇、`MemAvailable`の減少）。
10. **`EXP-008`はDT830Bで「約10〜20 mVの低下」を見ながら「有意性は判断しない」としていた。****今回の14.8 mVはその範囲に入る。**

### この記録が主張しないこと

- **`PWR IN`の入力電圧ではない。**M-12001のcableがreceptacleへ直挿しで触れられないため（`PSU-INGRESS-01`未着荷）、GPIO 40pinヘッダの`pin2`/`pin6`で代用した。**GPIOの5V pinはUSB入力と同一railだが、USB側にあるfuse／TVS／filterの保護回路を経由しない。****Zero Wの回路図は非公開であり、この保護回路による降下の有無・大きさは確認できていない。**`EXP-008`と同じ限定である。
- **絶対値の確度を主張しない。**rail換算の絶対値はAV<sub>CC</sub>の代理値5.04 V（最小単位10 mV）、分圧比の不確かさ、入力leakによる最大10 mVの系統offsetを含む。**精度が高いのは変化量の方である。**
- **DT830Bの確度そのものは取得できない。**`±10 mV`は最小単位から出る不確かさの下限であり確度ではない。
- **合否を判定していない。**`HW-TBD-023`と`HW-TBD-028`はTBDのままである。
- **star point構成を確定させていない。**あれはservo shunt側の話で、`PSU-INGRESS-01`の着荷後に残る。**`HW-TBD-034`の未解決3点のうち(3)は解けていない。**
- **cable差を検証していない。**それにはESP32の接続が要り、案Aにあたる。**この測定でESP32は接続していない。**
- **アイドル1の約100 msの乱れの原因を特定していない。**値が0付近であることは入力が一瞬開いた形と整合するが、**railが0 Vへ落ちたのではない**（Piは再起動していない）。**アイドル2とbuildでは再発していない。**
- **`EXP-009`の3回の停止について、この測定は何も語らない。**停止時にこの測定系は動いていない。
- **どのgateも開いていない。servoを繋いでいない。**

### 結論

- **Piの5 V入力を、1 channelあたり208 µs間隔・rail換算6.56 mV/LSBで観測できる測定系が成立した。**部品の着荷を待たずに組めている。
- **既知の負荷変化で波形が取れることを確認した。**`cargo build`で14.8 mVの低下が現れ、開始と終了に時間的に一致し、終了後に戻る。
- **対照chにより、AV<sub>CC</sub>の変動ではないことを分離できた。**`3V3`を同時に読む構成がこの分離を可能にした。**ただし`3V3`の生成経路をschematic粒度で確認していないため、これをAV<sub>CC</sub>の補正には使っていない。**
- **`HW-TBD-034`はcloseしない。**(3) GND topologyは`PSU-INGRESS-01`の着荷まで完了しない。**この測定で得た値を受け入れ判定に使わない。**
