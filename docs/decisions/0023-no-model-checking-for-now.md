# ADR-0023: サーボ安全制限と通信断の状態機械へ、いまモデル検査を導入しない

> 状態: Accepted
> 日付: 2026-09-17
>
> 起案: AIが起案した（2026-09-17）。**[#325](https://github.com/wachi-yoshitaka-11-dev/deskcat/issues/325)の候補3として、人間が対象を指定している。**
> **選択肢と決定の文面はAIが起案した。人間の承認はPull Requestのmerge承認として得る**
> （[ADR-0017](0017-what-counts-as-a-primary-source.md)・[ADR-0022](0022-wokwi-not-a-ci-simulation-gate.md)と同じ扱いである）。
>
> **この決定は「モデル検査が役に立たない」ではない。**対象が**まだ書けない**という判断である。
> 理由は判断要因3、再検討の条件は「検証」節が持つ。

## 背景

[#325](https://github.com/wachi-yoshitaka-11-dev/deskcat/issues/325)の候補3は、**サーボ安全制限と通信断処理の状態機械**に対して、
実装前に到達不能・deadlockを検査する手段（モデル検査）を使うかを問うている。
出所は Interface 2026年9月号である。**#325 本文はこれを[ADR-0017](0017-what-counts-as-a-primary-source.md)の丙と書いている。**
（**ADR-0017の区分そのものは、同ADRの「決定」8が「この区分は、安全要件5項目に効く値だけを対象とする」と定めている。**
誌面から受け取ったのは検証手法の提案であって値ではないため、**この ADR は丙の判定に依存しない。**
**[ADR-0022](0022-wokwi-not-a-ci-simulation-gate.md)は同じ出所を「丙である」と断定しており、そこだけ立ち位置が違う。**
**訂正はしない。**両者とも誌面を根拠にしないという結論は同じであり、**区分の当否はこの ADR の判断に効かない。**）
**#325 本文が「候補として挙げるだけであり、採否は DeskCat 側の根拠に基づいて決める」と定めている。**
いずれにせよ、**この ADR は誌面を根拠にしない。**

**#325 は条件を先に置いている。**「安全要件5項目のどれに効くかを示す（**効かないなら導入しない**）」
「対象の状態機械が状態爆発せずに書ける規模かを確認する」「検査 model と firmware 実装の乖離を防ぐ方法を決める」
「**検査が通ったことを安全要件の gate 通過と扱わない**ことを明記する」「導入する場合、tool の導入そのものは別 Issue にする」。
**この ADR はその条件に沿って判断する。**

## 判断要因

### 1. 5項目のうち、効きうるのは1つだけである

[Hardware Safety Policy](../governance/hardware-safety-policy.md)の安全要件5項目のうち、
**状態機械の性質が関係しうるのは「servoの持続的拘束」だけである。**

| 項目 | 状態機械が関係するか |
|---|---|
| 短絡 | しない。経路の最弱部品の定格と過電流保護の話である |
| 逆極性 | しない。配線と保護素子の話である |
| 給電経路の重複 | しない。電源系統の排他の話である |
| 電圧違いのpinへ挿す | しない。logic電圧と結線の話である |
| **servoの持続的拘束** | **しうる。**検知後に停止する経路と、通信断からの復帰経路が状態機械である |

**残る4項目は、model が何を証明しても変わらない。**

**この表は起案者の判断であり、policy の引用ではない。**
[Hardware Safety Policy](../governance/hardware-safety-policy.md)は各項目の性質を定めているが、
**「状態機械が関係するか」という列は同 policy に無い。**5項目の名前と性質の説明だけが同 policy のものである。

### 2. その1項目でも、モデル検査が示せるのは「与えた遷移の性質」だけである

「servoの持続的拘束」に対する予防は、[Servo Safety Limits](../hardware/servo-safety-limits.md#拘束stallと過負荷)が
**電流監視と時間base強制duty制限のうち「少なくとも一つ」を実装すること、
かつ時間base制限は常に必須で電流監視を採るなら併用すること**を定めている
（**「どちらか一方でよい」ではない。時間base制限は外せない。**）。
**しきい値・連続動作時間の上限・duty cycle窓は、model の外から与える数である。**

したがってモデル検査で言えるのは「**与えた遷移と与えた数の下で**、停止状態へ到達する」までである。
**数そのものの妥当性を、この repository は温度試験と電流試験に求めている。**
同文書の`動作制限`表が`最大連続動作時間`と`最大duty cycle`の根拠欄を「**温度／電流試験**」と定めており、
[TBD台帳](../hardware/tbd-register.md)の`HW-TBD-020`も「電流測定手段の選定＋温度／電流試験」を要求している。
（**引用元はこの2箇所であり、上でlinkした`拘束（stall）と過負荷`の節ではない。**）
**両文書が定めているのは「その試験を要する」ことであって、「他の手段では決して決まらない」ではない。**
**ここで言えるのは、モデル検査がその試験の代わりにならないことだけである。**

**この段落は起案者の判断であり、公式資料の引用ではない。**モデル検査一般の能力について、
この repository は資料を持たない（誌面は丙であり、この ADR は根拠にしない）。
**「与えた model の外にある数は検査で決まらない」という一点だけを根拠にしており、
tool ごとの能力差（時間つきの検査ができるか等）には踏み込んでいない。**
**踏み込む必要が出るのは、tool を選ぶときである**（判断要因6のとおり、この ADR は選んでいない）。

### 3. 対象の状態機械が、まだ書けない（**これが決定の理由である**）

**遷移が確定していない。**[TBD台帳](../hardware/tbd-register.md)の状態は次のとおりである（2026-09-17に確認）。

| ID | 対象 | 状態 |
|---|---|---|
| `HW-TBD-017` | 通信断の検知方式（heartbeat source、loss timeout） | **Open** |
| `HW-TBD-018` | 断時のfail-safe sequenceと、復帰時の再有効化条件・手順 | **Blocked**（`HW-TBD-010`・`HW-TBD-017`・`PROTO-TBD-013`による） |
| `HW-TBD-019` | 起動時とdriver故障時のサーボ出力状態（PWM driver初期化前のGPIO state、開始mode、enableまでのdelay、**Pi未接続時**、**reset後**、**driver故障検知時**） | **Blocked**（`HW-TBD-010`・`HW-TBD-027`による） |
| `HW-TBD-020` | 実行時のサーボ安全制御（検知手段、検知時の物理動作、復帰条件、しきい値、連続動作時間、duty cycle窓ほか） | **Blocked**（`HW-TBD-009`、全fieldのresolution evidence未記録、`PROTO-TBD-005`／`011`／`012`／`013`／`014`未解決による） |

**この4件を選んだ基準は「対象が状態機械の遷移そのものか」である。**
[サーボ出力を有効化してよい条件](../hardware/servo-safety-limits.md#サーボ出力を有効化してよい条件)の表は
12件のHW-TBD（`006`・`007`・`009`・`010`・`011`・`017`・`018`・`019`・`020`・`026`・`027`・`035`）を挙げている
（うち`006`は2026-08-05に解決済みで、表では打ち消してある）。
**残りは部品値・電気・機械の確定であって遷移ではない。**
**この基準で`HW-TBD-019`を外さない。**
**同項目は「Pi未接続時、reset後、driver故障検知時」を挙げている**（台帳の文言）。
**いずれもサーボ出力の状態がどう決まるかであり、状態機械の遷移そのものである**（この読みは起案者のものである）。
[サーボ出力を有効化してよい条件](../hardware/servo-safety-limits.md#サーボ出力を有効化してよい条件)も
同項目を1行として挙げている。**`017`・`018`・`020`の3件だけで条件を組むと、起動時とdriver故障時の遷移が抜ける。**

Protocol 側も同じである。`PROTO-TBD-010`（heartbeat方式とlink-loss判定）、`011`（`sid`生成とretired session）、
`012`（受理上限とsession遷移の上限）、`013`（stale commandの拒否条件）、`014`（fault eventの名前とschema）は
**いずれも未解決であり、5件とも[Protocol §13](../protocol/esp32-pi-protocol.md#13-未決定事項)が
「サーボ出力の有効化条件に含まれる」と明記している。**

**ここで挙げた5件と、上表の`HW-TBD-020`行が挙げる5件は別の集合である。**前者は`010`〜`014`、
後者は`005`・`011`〜`014`であり、**`010`は後者に無く、`005`は前者に無い。同じ「5件」と読まない。**

**ただし`005`が有効化条件の外にあるという意味ではない。**
[Protocol §13](../protocol/esp32-pi-protocol.md#13-未決定事項)は`PROTO-TBD-005`にも
「サーボ出力の有効化条件に含まれる」と書いており、
[サーボ出力を有効化してよい条件](../hardware/servo-safety-limits.md#サーボ出力を有効化してよい条件)も
`HW-TBD-020`／`PROTO-TBD-005`／`011`／`012`／`013`／`014`を1行に挙げている。
**有効化条件に含まれるProtocol TBDは`005`を足した6件である。**
上の5件は、**この ADR の本文が通信断とサーボ安全制限の両側から列挙した範囲**にすぎない。
**対で確定する相手は、[TBD台帳](../hardware/tbd-register.md)のHW↔PROTO対応表が定めている**
（`servo-safety-limits.md`が「対応関係の正本は同表である」と書いている。§13にも対の記述が在るが参照側である）。
`PROTO-TBD-010`は`HW-TBD-017`、`013`は`HW-TBD-018`と`HW-TBD-020`、
`011`・`012`・`014`は`HW-TBD-020`である。**5件をまとめて一つのHW-TBDの側と読まない。**

[Servo Safety Limits](../hardware/servo-safety-limits.md#通信断時動作)の通信断時動作は、
**「短時間保持して低速でneutralへ移動しdisable」「現在位置を保持」「直ちにPWMをdisable」の3案を並べたまま**であり、
**どれを採るかが決まっていない。**

**この状態で model を書くと、検査するのは私が仮定した遷移である。**仕様でも実装でもない。
**#325 が要求する「検査 model と firmware 実装の乖離を防ぐ方法」は、片側が存在しないあいだは決められない。**

### 4. 対象の状態機械は、Rust 実装のどこにも無い

**確認したのは Rust 実装の全体である**（2026-09-17）。
**DeskCat 本体は Rust で書かれているが、「本体 code は Rust だけ」を全称では主張しない**（後述）。
**確認方法をここへ書く。**後日の読み手が同じ手順を踏めるようにするためである。

1. `git ls-files '*.rs'` で対象を取った。43 fileあり、**すべて`firmware/esp32`配下と`crates/`配下である**
   （`firmware/esp32/src` 5、`firmware/esp32/build.rs` 1、`crates/`の4 package 37。後者は`src`・`tests`・`examples`を含む）
2. `crates/`のCargo packageは`deskcat-config`／`deskcat-protocol`／`deskcat-serial`／`deskcat-servo`の4件である
   （`firmware/esp32`も独立したpackageであり、repository全体では5件になる）。
   `crates/deskcat-api`／`deskcat-domain`／`deskcat-storage`の3 directoryと
   `apps/deskcatd`／`simulator/deskcat-sim`／`tests/hil`は、**いずれも`README.md`だけで`.rs`を持たない**
3. 1で取った`.rs`を対象に、`heartbeat`／`link-loss`／`fail-safe`／`拘束`／`通信断`／`servo` を
   **`grep -i`（大文字小文字を区別しない）**で当て、当たった行と各 crate の module doc を読んだ

**手順1〜3は`.rs`に閉じている。Rust以外は数え切っていない。**repository内のRust以外は
`scripts/`（Python。CIとgovernanceのtooling）、`.github/`（CI workflowとtemplate、label定義）、
`hardware/measurement/`（Arduinoのsketchと測定script）、`pages/`（HTMLとSCSS。[ADR-0009](0009-pages-own-layout.md)）、
および repository 直下の設定 file である。**この列挙は網羅ではない。**
**いずれも本体を動かすcodeではないため、この ADR の対象から外した。**
**「Rust以外に本体codeは無い」と全称で主張しない。**主張するのは、
**Rust実装を全数見た結果、対象の状態機械がそこに無いこと**だけである。このうち`hardware/measurement/`だけは、
ESP32以外のマイコンを扱うため念のため`grep -i`で当てたが、上の語のどれも含まない（0件）。

**まず、状態を持つ実装は在る。**

- `firmware/esp32/src/protocol.rs` の `PiSession` は現在の Pi `sid` と retired `sid` を持つ。
  **session を遷移させるのは `handle_hello`（§5.1）だけである**（`&mut self`）。
  `handle_get_status`（§5.6）と `handle_ping`（§5.7）は `&self` を取り、現在の `sid` と照合して
  `stale_session` を返すかどうかを決めるだけで、状態を変えない。
  `main.rs` の `demonstrate_pi_session` が3つとも実際に動かしている
- host 側の `crates/deskcat-serial/src/peer.rs` は ESP32 側の session 遷移、duplicate 履歴、`stale_session` 判定を持つ
- **`crates/deskcat-serial/src/session.rs` は、transport 層の断と再接続を状態機械として持つ。**
  `ConnectionState`（`Disconnected`／`Connected`／`Stopped`）、`note_disconnected`、
  有限予算つきの `begin_reconnect`、`StopReason::ReconnectExhausted`、counter `disconnects`／`reconnect_attempts` である

**しかし、この ADR の対象はそこではない。**対象は
[AGENTS.md](../../AGENTS.md)「プロジェクト境界」が **ESP32 に強制させると定めた通信断処理**と、
**サーボ安全制限**の状態機械である。**それは確認した範囲のどこにも無い。**

- `session.rs` が検知するのは **Pi 側の serial port の I/O 断**であり、
  **heartbeat による link-loss 判定ではない。**それは `PROTO-TBD-010`／`HW-TBD-017` として未確定である
  （判断要因3）。同 file の再接続予算も transport を開き直す話であって、**断のあいだサーボをどうするかには触れない**
- **断に対するサーボの動作（`HW-TBD-018`）は、確認した範囲のどこにも無い。**そもそも駆動する servo 出力が無い。
  `main.rs` の comment は「**`Peripherals::take()`はLCD配線の分だけ。**servoやI2C sensorは触らない」と書く。
  **code 上は `Peripherals::take()` が集合をまるごと取り、それを `run_display_bringup` へ渡している。**
  comment が言っているのは**使う範囲**である。**servo pin を駆動する経路はどこにも無い。**
  `firmware/esp32/src` を `ledc`／`pwm` で `grep -i` すると当たるのは doc comment 2行だけで、
  **API の呼び出しは1つも無い**（`main.rs` の「`SERVO-PWM`…はこの版でも一切触れない」と
  `display.rs` の「PWM調光は将来検討」である）。同 file の
  `peripherals=display_only servo=not_driven` という log も同じことを述べるが、
  **log は code 自身の主張であって観測ではない。**根拠は上の grep の側である
- `crates/deskcat-servo` の `src` は4 file（`lib.rs`／`limiter.rs`／`limits.rs`／`counters.rs`）だが、
  **crate 全体（`tests`を含む）で heartbeat、link-loss判定、fail-safe sequence、拘束検知のいずれも持たない。**
  上の3の手順で当たる行は5 fileに散るが、**`servo`（crate名・型名・path・module doc の責務記述）を除くと、
  残りはすべてdoc commentであり、実装は1つも無い。**
  `src/limits.rs`は「`neutral`はfail-safeの行き先の候補」、`src/counters.rs`は位置と加速度が両立しないとき
  加速度を譲る理由が「servoの持続的拘束」に効くためであること、`tests/trajectory.rs`は
  `HEARTBEAT_PERIOD_MS`とは無関係である旨、`src/limiter.rs`は「起動時のservo位置がfirmwareから分からない」
  （`HW-TBD-019`への言及）である。**このうち中2つは要旨であり、逐語ではない。**
  **ここでの判定は件数ではなく、当たった行に実装が1つも無いことである。**
  同 crate の module doc は「**このcrateは境界値を持たない**」「可動域、速度、加速度……**すべて呼び出し側から受け取る**」
  と書く。`Limiter::admit`／`step` は trajectory limiting であって、断や拘束からの遷移ではない
- `peer.rs` の module doc は `PROTO-TBD-011`／`PROTO-TBD-012`／`PROTO-TBD-017` を挙げて
  **「未確定であり、ここでは実装しない」**と明記している

> **`heartbeat` という名前の付いたものは在るが、これではない。**firmware では
> `config.rs` の `HEARTBEAT_PERIOD_MS`（1000 ms。同 file は「**暫定値である。**」としたうえで、
> Protocol §5.7 が `ping` について「Heartbeatの最終用途とintervalは`TBD`とする」としていることを理由に
> 「**この値に一次資料の根拠は無い**」と書く）、
> `main.rs` の周期 log 出力（`hb seq=`）と bring-up 各段で1回出す `bringup_hb seq=`
> （**`main.rs` 自身が「`bringup_hb`と`hb`は別の名前にする」と書き分けている**）、
> `health.rs` の `heartbeat_seq` である。
> crate 側では `deskcat-protocol` の `Message::Ping` の doc が「payloadを持たないheartbeat（§5.7）」と書いている。
> **`Ping` は message type であって、link-loss を判定する側ではない。**
> **これは log と health snapshot の tick であって、wire へ出す heartbeat でも link-loss 判定でもない。**
> **firmware 側に実 serial link がまだ無い。**`firmware/esp32/src/protocol.rs` の module doc が
> 「**実serial linkからこの型へbyteを渡す配線は、GPIO割り当てではなく、UART0の出力先の未決で止まっている**」と書く。
> **依存関係ではなくこの記述が根拠である**（firmware が `deskcat-serial` を引いていないことは、
> 同 crate が host 側であるため link の有無とは独立である）。
> host 側の `crates/deskcat-serial` には `serial2` を使う `SerialDevice` が在り、
> `examples/serial_link.rs` も「実serial portへ繋いでlinkを確かめる実行体」として在る。
> **ただし同 example の doc 自身が「`ESP32`側がprotocolを話すとは限らない」と書いている。**
> 実行の記録も無い。[Raspberry Pi の toolchain 記録](../toolchains/raspberry-pi-rust-toolchain.md)が
> 「**実 serial port を開いていない。`serial_link` example は build しただけである**」と書いている。
> **何を heartbeat とするかは
> `PROTO-TBD-010`／`HW-TBD-017` として未確定である**（判断要因3）。

**未確定な部分は、実装側でも意図的に空けてある。**heartbeat で断を判定する経路も、
断のあいだサーボを安全側へ置く経路も、拘束を検知して停止する経路も無い。
**この ADR の対象については、乖離を検出する相手が存在しない。**

> **`firmware/esp32/src/health.rs` の記述を2点、現況と照合した。**
> module doc は「この firmware は serial link（#11）も **session state（#12）も持たない**ため
> `ProtocolCounters` はすべて 0 のままである」と書く。**counter が 0 である結論は正しいが、
> 理由の片方「session state を持たない」は現況と合わない。**上のとおり `PiSession` は在る。
> **counter が 0 であること自体は、doc の理由によらず code から言える。**`firmware/esp32/` の `.rs` を
> `counters` で当てると（**型名`ProtocolCounters`を除くため、ここだけ大文字小文字を区別する**）
> `health.rs` の3箇所だけで、field 宣言・`ProtocolCounters::default()` の代入・
> `to_status` での読み出しである。**加算する経路がどこにも無い。**
> **この ADR が使うのはこの事実だけであり、doc が挙げた2つの理由のどちらも採らない。**
> `UNKNOWN_STATE` の doc comment も古い。「`Peripherals::take()` を呼ばず、display も servo も
> sensor も存在しない」と書いているが、**LCD bring-up（#13）が入った後の `main.rs` は
> `Peripherals::take()` を呼び、`display.rs` が在る。**
> **この ADR は、どちらの doc comment でもなく現在の code から判断している。**
> 訂正は `firmware/` の変更であり、**この ADR の範囲外として手を付けていない。**

### 5. 「状態爆発せずに書ける規模か」は、いまは測れない

#325 はこの確認を求めている。**しかし状態数は、遷移が決まってから数えるものである。**
判断要因3のとおり遷移が未確定であり、**いま出せるのは「小さそうだ」という見込みにすぎない。**
**見込みを「確認した」と書かない**（`AGENTS.md`「検証」の
「実行できなかった check を、成功したものとして扱わない」）。

**確認そのものが、遷移の確定を待っている。**

### 6. tool の導入には、別の前提が要る

`AGENTS.md`「開発端末の役割」は、**ツール導入を「対象 Issue、端末 profile、人間の確認が揃った開発端末だけ」**に限っている。
[AI Agent Policy](../governance/ai-agent-policy.md)も「重要な新規外部依存またはtoolの導入」を人間の確認が要る操作へ挙げている。
**#325 の候補3自身も「導入する場合、tool の導入そのものは別 Issue にする」と定めている。**

**この ADR では tool を選んでいない。**採否の判断だけを行う。

## 検討した選択肢

### 選択肢A: いま model を書いて検査を導入する

通信断とサーボ安全制限の状態機械を起案し、到達不能とdeadlockを検査する。

**利点。**実装が書かれる前に、遷移の穴（断を検知したが停止しない、復帰して即座に再拘束する等）を見つけられる。
**穴が実装に入ってからでは、実機で踏むまで分からない。**

**コスト。**判断要因3のとおり、**検査するのは起案者が仮定した遷移である。**
仕様が後から別の遷移を採れば、検査結果は無効になる。**さらに悪いのは、無効になったことに誰も気付かない場合である。**
[通信断時動作](../hardware/servo-safety-limits.md#通信断時動作)が3案を並べたままである以上、
**仮定は当たらない方が確からしい。**

### 選択肢B: いま導入しない。遷移が確定した時点で再検討する

`HW-TBD-017`／`018`／`019`／`020`が閉じ、状態機械が仕様として書ける状態になってから判断する。

**利点。**仮定した model を検査する無駄が無い。**再検討の条件を残せるため、判断が忘れられない。**

**コスト。**遷移が確定するまでのあいだ、仕様の穴は人間の読みでしか見つからない。
**ただし2026-09-17時点では、対象の状態機械は実装にも無い**（判断要因4）。
**そのあいだは、サーボ安全制限にも通信断の fail-safe にも、実装前に踏める穴は無い。**
**ただし有効化gateが止めているのはサーボ出力であって、code の先行実装ではない。**
**遷移が確定する前に実装が書かれることはありうる。**そのときはこのコスト評価が変わる（検証節を参照）。

### 選択肢D: いま model を書くが、検査ではなく「3案の比較」に使う

**DをCの前に置いた。**DはBのすぐ後に来る「model の別の使い道」の検討であり、
Cは再検討の有無という別の軸だからである。**優劣の順ではない。**採否はlabelで参照する。

[通信断時動作](../hardware/servo-safety-limits.md#通信断時動作)は3案を並べたまま選択を待っている。
**確定した遷移を検査するのではなく、3案それぞれを model にして違いを見る**という使い方はありうる。

**利点。**仮定ではなく、**文書が並べた3案そのもの**を対象にできる。選択肢Aの弱点を避けられる。

**コスト。****3案の選択を決めるのは、model が答えられる性質ではない。**
同文書は「**PWMをdisableにしたときに首が落下したり予期せず動いたりするかを考慮して選択する**」と書いている。
そして[TBD台帳](../hardware/tbd-register.md)が、`HW-TBD-018`の`必要な根拠`欄を
「**監視下の機械試験**（PWM断時の首の挙動、および復帰時の挙動）」と定めている
（**この文言が在るのは台帳のこの欄である。**fail-safe 動作そのものの正本は
`servo-safety-limits.md`であり、台帳の同じcellもそう書いている）。
**落下するかどうかは機構と重量の性質であり、到達可能性の検査では出ない。**
3案は到達する状態の集合が違うのではなく、**同じ「出力を止める」へ至る過程の物理が違う。**

**したがって、この使い方でも選択は進まない。**model は3案を書き分けられるが、**選べない。**

### 選択肢C: 導入しないと決め、将来も再検討しない

**利点。**判断が1回で終わる。

**コスト。**判断要因1・2は「効かない」ではなく「**効く範囲が1項目で、しかも数の妥当性までは示せない**」である。
**効く範囲が在るものを、永久に閉じる理由がない。**

## 決定

**選択肢Bを採る。いまは導入しない。**

**これは「モデル検査が役に立たない」という判断ではない。**判断要因1・2のとおり効く範囲は在る。
**導入しない理由は、判断要因3のとおり対象の状態機械がまだ書けないことである。**

- モデル検査の tool を選ばない。導入しない。CI にも検証手順にも入れない
- **`docs/` にも `firmware/` にも、検査 model を置かない**
- **再検討の条件を「検証」節へ残す。**条件が揃ったときに判断し直す

**将来 A を採る場合に備えて、#325 が先に置いた条件をここへ確定させておく。**
**これは導入の予告ではない。**導入するなら最低限これを満たす、という線である。

1. **検査が通ったことを、安全要件の gate 通過として扱わない。**
   サーボ出力の有効化条件の正本は
   [サーボ出力を有効化してよい条件](../hardware/servo-safety-limits.md#サーボ出力を有効化してよい条件)であり、
   **モデル検査はそこに無い。**追加するなら同文書の改訂として行う。**この ADR は追加しない。**
2. **model が通ったことを、実装の保証として扱わない。**検査するのは model であって firmware ではない。
   **乖離を防ぐ方法を決めてから導入する**（#325 の条件）。決められないなら導入しない。
3. **tool の導入は別 Issue にする。**端末 profile と人間の確認が揃った開発端末だけで行う
   （`AGENTS.md`「開発端末の役割」）。**Docs／Review 端末へ入れない。**

## 影響

### 利点

- 仮定した遷移を検査して「確かめた」と記録することを避けられる
- 保守対象が増えない。model も tool も CI job も増えない
- **判断が残る。**#325 の候補3が「何も決めずに閉じた」状態にならない

### 欠点

- 遷移が確定するまで、仕様の穴は人間の読みでしか見つからない
- **再検討の条件が揃ったときに、誰かが気付く必要がある。**自動では起きない

### リスクと対策

| リスク | 対策 |
|---|---|
| 「モデル検査は不要」と誤って引用される | 冒頭と決定節に**「対象がまだ書けない、という判断である」**と明記した。判断要因1・2（効く範囲が在る）と3（いま書けない）を分けてある |
| 再検討の条件が揃っても忘れられる | 条件を`HW-TBD-017`／`018`／`019`／`020`のcloseへ結び付け、[TBD台帳](../hardware/tbd-register.md)の`HW-TBD-020`のclose条件の直後へ見直し指示を置いた（**同じ節に`017`・`018`のclose条件も在る**）。**これは「読まれる可能性を上げる」対策であって、強制ではない。**hookもCIも見ていない。**`019`のcloseだけを行う読み手がこの節へ来る保証も無い。****欠点欄に書いたとおり、気付くのは人である** |
| 将来 A を採るとき、gateの扱いが緩む | 決定節の3条件を先に確定させた。**とくに「gate通過として扱わない」は、導入の可否とは独立に成立する** |

## 検証

**この決定は、次の4つが揃ったときに見直す。この4つが条件の正本である。**
**[TBD台帳](../hardware/tbd-register.md)にも同じ見直し指示を置いたが、条件の中身はここが持つ。**

1. **`HW-TBD-017` が close している**
2. **`HW-TBD-018` が close している**
3. **`HW-TBD-019` が close している**
4. **`HW-TBD-020` が close している**

**「close」は台帳が定める意味で読む。**各 TBD の close 条件は[TBD台帳](../hardware/tbd-register.md)が持ち、
**ここへ再掲しない。要約もしない。**

**写してよいものと写さないものを、ここで分けておく。**判断要因3の表は台帳の`不足している情報／判断`と`状態`の2列を
**日付つきの抜粋として**載せている（この ADR の表では前者を`対象`と呼んでいる）。
**全行が逐語というわけではない。**`HW-TBD-020`は同列が括弧内に挙げる項目を「…ほか」で畳み、`HW-TBD-018`も短縮した。
`対象`列に限れば`HW-TBD-017`と`HW-TBD-019`は逐語である。
**`状態`列は4行とも書き換えてある。**台帳が裸の番号で書く blocker を完全IDへ展開した
（`HW-TBD-010`と`PROTO-TBD-010`を取り違えないためである）。
**遷移が確定していないことを示すのに足りる粒度まで削ってある。**値の判定にはこの表を使わず、台帳を開く。
**とくに`HW-TBD-020`のcloseが要求する「全field」は、この列の括弧内ではなく
[台帳の`HW-TBD-020`のfield単位の正](../hardware/tbd-register.md#hw-tbd-020のfield単位の正)の表である。**
**件数をこの ADR から数えない。**
`HW-TBD-019`の`reset後`は、正本の[起動時とdriver故障時の動作](../hardware/servo-safety-limits.md#起動時とdriver故障時の動作)では
`Watchdog、panic、brownout reset後`と限定されている。**この表はその限定を持たない台帳側の文言を載せている。**判断の前提を読み手が追えるようにするためであり、
**台帳が動けばこの ADR 側が古くなる**（表の直上にその日付を書いてある）。
**close条件は写さない。**写した瞬間に台帳より弱い版が生まれ、どちらでcloseしてよいかが二つになるためである。

**「写さない」が禁じているのは、台帳より弱い版を作ることである。**逐語の参照はそれに当たらない。
この ADR が台帳の close 側の記述を引くのは、`必要な根拠`欄が3箇所
（判断要因2の`HW-TBD-020`、選択肢Dの`HW-TBD-018`、この節の`HW-TBD-019`）、
close条件の散文が2箇所（この節の`HW-TBD-018`と、同じくこの節の「全field」）である。
**いずれも逐語であり、要約していない。****どれも「台帳がこう定めている」という参照であって、
この ADR がcloseの可否を判定するために使ってはいない。**判定は台帳が行う。

**台帳側には、この ADR の再検討条件の中身を置かない。**台帳が持つのは、この決定の理由の一文、
見直しの起点となるID 4件、それが何を意味しないかの注意、`019`を4件から外さないための注意、
`019`を遷移と数えるのが起案者の読みであることの断り、範囲の参照先、
その段落をあの節へ置いた理由、および正本がどちらにあるかの明示である。
**各TBDのclose条件がどちらの文書に属するかは、上の線引きのとおりである。**
**ただし`HW-TBD-019`だけは、「何が確定したらcloseしてよいか」を述べた散文を台帳が持たない**
（`017`・`018`・`020`のものは`HW-TBD-020のfield単位の正`の節に在る。`019`のものは台帳のどこにも無い。
**同IDを名指しした散文は`対応Issue列`の`記載規則`に在るが、そちらは対応Issueの判定規則であってclose条件ではない**）。**同項目にも表の`必要な根拠`欄（無負荷でのPWM測定＋起動時glitch確認）は在り、
要件が無いという意味ではない。**close の手順は台帳の「解決手順」節に従う。
**この ADR が代わりの条件を書かない。**とくに`HW-TBD-020`の close 条件は長く、
**要約すると必ず台帳より弱くなる。**台帳の当該段落をそのまま読む。
**「状態機械に効くfieldだけ確定した」を close と読み替えない。**台帳より弱い条件を、この ADR が別に作らない。

**1つでも欠けていれば、状態機械は仕様として書けていない。**そのあいだは再検討しない。

**この4件は、再検討を始めてよいかを決める条件である。**判断要因3が挙げた残り2つが、
この4件の外へこぼれないことを確かめておく（**3つ目のbulletは、こぼれる側の1件である**）。

- **Protocol TBD は、台帳の「登録範囲」節にある HW↔PROTO の対応表**
  （列は`このIDの正`／`対応するprotocol側ID`／`field単位の正`）**が割り当てている。**
  `PROTO-TBD-010`は`HW-TBD-017`、`PROTO-TBD-013`は`HW-TBD-018`と`HW-TBD-020`、
  `PROTO-TBD-005`・`011`・`012`・`014`は`HW-TBD-020`である。
  **`HW-TBD-019`の欄は`—`であり、対応するProtocol TBDを持たない。**
  **`PROTO-TBD-010`を`HW-TBD-018`や`HW-TBD-020`の側に数えない。**同表で`PROTO-TBD-010`が
  対応するのは`HW-TBD-017`だけである（**`HW-TBD-010`とは別のIDである。**判断要因3の表で
  `018`・`019`のblockerに在るのは`HW-TBD-010`のほうであり、`PROTO-TBD-010`ではない）
- **[通信断時動作](../hardware/servo-safety-limits.md#通信断時動作)の3案の選択は、`HW-TBD-018`のclose条件が要求している。**
  台帳が同項目を「fail-safe sequenceとrecovery／reconnect動作の両方が確定するまでcloseしない」と定めている
  （**逐語であり、要約していない。**この節が台帳の close 側から引く箇所は上に数え上げてある）
- **`PROTO-TBD-017`（`boot`再送のparameterとrecovery budget）は、この4件に紐づかない。**
  判断要因4で`peer.rs`の「ここでは実装しない」の一例として引いたが、台帳のHW↔PROTO対応表に同IDの行は無く、
  [Protocol §13](../protocol/esp32-pi-protocol.md#13-未決定事項)も同IDを「サーボ出力の有効化条件に含まれる」とは書いていない。
  **つまり4件がcloseしても`PROTO-TBD-017`は開いたままでありうる。**
  **この ADR はそれを承知で4件を条件とする。**再検討の起点はサーボ安全制限と通信断の遷移であって、
  `boot`の再送予算はその遷移に含まれないためである

**この ADR はそれらを自分の条件として書き直さない。**台帳が要求を緩めれば、この4件も同じだけ緩む。
**4件のcloseは「遷移が確定した」ことの保証ではなく、確定したかを見に行く合図である。**

**揃った時点で最初に確認するのは、#325 が求めた「状態爆発せずに書ける規模か」である**（判断要因5）。
**遷移が確定して初めて数えられる。**

**実装側の状態は、再検討の条件に入れていない。**4つが close した時点で実装が在るとは限らないためである。
**ただし#325 が求める「乖離を防ぐ方法」は実装側を要する**（判断要因4）。
**再検討の時点で実装が無ければ、その条件は依然として決められない。**そのときは
**判断要因4を測り直す。**4つの close だけで「乖離を防ぐ方法が決まる」と読まない。

## 置き換える決定

なし。
