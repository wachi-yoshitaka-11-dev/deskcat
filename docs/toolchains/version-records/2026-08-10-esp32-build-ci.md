## 所要時間

同一 commit に対する 2 回の実行である。2 回目は 1 回目が保存した cache を復元している。

| step | cache 無し（初回） | cache 有り（2 回目） |
|---|---|---|
| Set up job | 1 s | 2 s |
| Checkout | 0 s | 1 s |
| Cache restore | 1 s（miss） | 8 s（hit） |
| Install Xtensa Rust toolchain | 58 s | 53 s |
| Format | 0 s | 0 s |
| Lint | 263 s | 185 s |
| Build | 19 s | 14 s |
| Cache save | 5 s | 0 s（primary key hit のため保存しない） |
| **合計** | **349 s（5 分 49 秒）** | **264 s（4 分 24 秒）** |

**差は 85 秒（約 24 %）である。**

cache 対象は `~/.cargo/registry`、`~/.cargo/git`、`firmware/esp32/target` の 3 つで、
復元 size は 327 MB だった。

**`.embuild` は cache していない。**`.cargo/config.toml` が
`ESP_IDF_TOOLS_INSTALL_DIR = "workspace"` を固定しており、ESP-IDF 本体と managed tool が
ここへ入る。開発端末での実測は 4.4 GB であり、repository あたりの cache 上限 10 GB に対して
大きい。単一 entry が上限の半分近くを占めると、LRU eviction で他の cache を追い出す。

その結果、**ESP-IDF の取得と build は毎 run 発生する。**cache 有りでも `Lint` が 185 秒
掛かっているのは主にこの分である。cache が効いているのは crate の取得と再 compile であって、
支配的な部分ではない。24 % という改善幅はこの構造による。

## artifact の同一性について

**本記録は成果物の sha256 を取得していない。**開発端末の記録が
「記録した入力を揃えても sha256 は一致しなかった（実測）」と結論しており、
環境が違う CI で一致を期待する根拠が無い。**取得しても比較の基準にできないため取らない。**

本記録が主張するのは、**同じ commit と同じ lockfile が、別環境で clean build を通ること**である。
`--locked` が成功していることは、`Cargo.lock` からの逸脱が無いことを示す。

「container で得た結果を実機の根拠として扱わない」制限は flash と実機試験に掛かる。
本記録は build-only であり、flash と実機起動を主張しない。

## 制限

- **実機動作を一切主張しない。**flash、serial monitor、boot 確認は [#6](https://github.com/wachi-yoshitaka-11-dev/deskcat/issues/6) の範囲である
- runner image は GitHub が更新する。将来の run が同じ image とは限らない
- toolchain 名の一致は強制されるが、**その名前の中身が本当に 1.95.0.0 かは検査していない**（[#74](https://github.com/wachi-yoshitaka-11-dev/deskcat/issues/74) の残る穴と同じ）。CI では action の `version` 入力が版を決めている
- peak memory と storage delta は未測定である
