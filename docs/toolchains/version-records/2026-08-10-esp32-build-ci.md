## 所要時間

下表は上表の run 1〜3 の内訳である。run 1 は cache 無し、run 2 と 3 は run 1 が保存した cache を復元している
（いずれも `Cache hit ... on the primary key`）。

| step | cache 無し（1 回目） | cache 有り（2 回目） | cache 有り（3 回目） |
|---|---|---|---|
| Set up job | 1 s | 2 s | 1 s |
| Checkout | 0 s | 1 s | 1 s |
| Cache restore | 1 s（miss） | 8 s（hit） | 8 s（hit） |
| Install Xtensa Rust toolchain | 58 s | 53 s | 62 s |
| Format | 0 s | 0 s | 0 s |
| Lint | 263 s | 185 s | 219 s |
| Build | 19 s | 14 s | 20 s |
| Cache save | 5 s | 0 s | 0 s |
| **合計** | **349 s** | **264 s** | **311 s** |

cache 対象は `~/.cargo/registry`、`~/.cargo/git`、`firmware/esp32/target` の 3 つで、
復元 size は 327 MB（342,784,591 B）だった。

run 5（cache 有り）は **299 s** だった。cache 有りの実測は **264 s / 299 s / 311 s** の 3 点である。

### この数字をどう読むか

cache 有りの 3 回が **264 s / 299 s / 311 s** と 47 s の幅でばらついている。`Lint` 単体でも 185〜219 s である。
**cache による差（349 s に対して 38〜85 s）は、runner 側のばらつきと同じ桁にある。**

したがって **この試行回数では「cache で何 % 速くなる」と言える精度が無い。**
言えるのは次の 2 点だけである。

- cache 有りの 3 回は、いずれも cache 無しの 1 回より速かった
- 差は最大でも 85 s であり、**全体（約 5 分）を大きく変える規模ではない**

`.embuild` を cache しない構成では、**ESP-IDF の取得と build が毎 run 発生する。**
cache 有りでも `Lint` が 185〜219 s 掛かるのは主にこの分である。cache が効いているのは
crate の取得と再 compile であって、支配的な部分ではない。
所要時間を本気で縮めるなら、**削るべきは `.embuild` の再取得であって、この cache ではない。**
それは上限 10 GB との兼ね合いで採らなかった（次節）。

### `.embuild` を cache しない判断

`.cargo/config.toml` が `ESP_IDF_TOOLS_INSTALL_DIR = "workspace"` を固定しており、
ESP-IDF 本体と managed tool が `.embuild` へ入る。開発端末での実測は **4.4 GB** であり、
repository あたりの cache 上限 10 GB に対して大きい。単一 entry が上限の半分近くを占めると、
LRU eviction で他の cache を追い出す。

**この判断の代償は上の所要時間そのものである。**速度を取るなら `.embuild` を cache する側に
倒すことになるが、その場合は上限との兼ね合いを別途評価する必要がある。
現状は「毎 run 約 5 分」を受け入れて、cache 上限を圧迫しない側を選んでいる。

## artifact の同一性について

**本記録は成果物の sha256 を取得していない。**開発端末の記録が
「記録した入力を揃えても sha256 は一致しなかった（実測）」と結論しており、
環境が違う CI で一致を期待する根拠が無い。**取得しても比較の基準にできないため取らない。**

本記録が主張するのは、**同じ commit と同じ lockfile が、別環境で clean build を通ること**である。
`--locked` が成功していることは、`Cargo.lock` からの逸脱が無いことを示す。

## 制限

- **実機動作を一切主張しない。**flash、serial monitor、boot 確認は [#6](https://github.com/wachi-yoshitaka-11-dev/deskcat/issues/6) の範囲である
- runner image は GitHub が更新する。将来の run が同じ image とは限らない
- **CI では compiler の実体を観測している。**`Record toolchain versions` step の `rustc --version --verbose` が `1.95.0.0` を出力しており、[#74](https://github.com/wachi-yoshitaka-11-dev/deskcat/issues/74) が残した穴（名前は合っているが中身が違う）は、**CI 上に限っては塞がっている**。ただし出力を記録するだけで、**期待値と自動照合してはいない**。手元 build も対象外である
- peak memory と storage delta は未測定である
- **`ldproxy` の版は取得できない。**linker wrapper であり `--version` を受け付けず、単体実行すると
  `Cannot locate argument '--ldproxy-linker <linker>'` で panic する。導入の確認は path 解決までである
