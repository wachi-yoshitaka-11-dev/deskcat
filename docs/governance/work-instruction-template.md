# 作業指示書テンプレート

> 状態: Active
> 適用範囲: 人間・PM・別のAIセッションから1つの作業を渡す指示書・引き継ぎ

作業指示書は repository の正本文書ではない。**`WORK-INSTRUCTIONS-*.md`は`.gitignore`済みで
git に入らない。**次の担当に必要な内容は既存Issue／PRへ保存し、そのURLを渡す。
ローカル指示書だけを必須情報の保存先にしない。保存後、不要なローカル指示書は削除してよい。

## この様式が要る理由

**2026-08-25に実測した。**`WORK-INSTRUCTIONS-*.md` 8本のうち、
`完了条件`は8本、`絶対に守ること`は6本、`Pull Requestの規約`と`触らないもの`は5本、
`他の作業との衝突`は5本にある。共通見出しの配下は**1本あたり8〜73行（中央値52行）**を占める。

**この数はrepository外のfileを測ったものであり、repositoryからは追検証できない。**
`WORK-INSTRUCTIONS-*.md`は`.gitignore`済みで、どのbranchにも入らない。
**数を根拠として引き継ぐ場合は、その時点で測り直す。**

**そのうち`Pull Requestの規約`と`触らないもの`の大半は
[CONTRIBUTING](https://github.com/wachi-yoshitaka-11-dev/deskcat/blob/main/CONTRIBUTING.md)の
再掲である。**同じ指示書が冒頭で「CONTRIBUTINGを読む」と書いている。

**書いてあることは、埋もれると踏まれる。**`review`と`full review`の使い分けは
[CONTRIBUTING](https://github.com/wachi-yoshitaka-11-dev/deskcat/blob/main/CONTRIBUTING.md)が
節を立てて説明し、[ADR-0013](../decisions/0013-manual-only-coderabbit-review.md)が
「この手順を変えない」と決定しているが、それでも空振りは起きている
（CONTRIBUTINGの「5行目の観測」に、1回目が空振りした記録がある）。

**定型が長いほど、その中の1行は読まれない。**指示書から定型を落とす理由はこれである。
**読む側が定型を飛ばす習慣を作らない。**

## 書き方

**3つだけ守る。**

1. 冒頭で対象base branchと確認したcommit SHAを示し、その版のCONTRIBUTINGと
   「全体の流れ」を参照する。下の一般リンクも、実作業では対象baseの版で読む
2. **その作業に固有のことだけを書く**
3. **CONTRIBUTINGの中身を写さない。**PR規約、trailerの書式、自己レビューの収束条件、
   CodeRabbitの依頼手順は、すべてCONTRIBUTINGが正本である

既存規則の確認先を示し、同じ規則の本文を増やさない。

**実行できるものは`.claude/skills/deskcat-preflight`が持つ。**着手前・push前・merge前・
merge後に機械で確かめられることをまとめてある。**同skillも規則を持たず、CONTRIBUTINGを
参照する。**指示書からはskillの名前を挙げるだけでよい。

## 様式

```text
# 作業指示: <Issue番号> — <一文の目的>

> 作成者: <人間／PM・AIの別、日付>。人間review: <未／判断元URLと対象範囲>
- Issue: #<番号>（<milestone>、<label>）
- 基点: <base branch> @ <完全なcommit SHA>（<確認日時>）
- 端末: <Machine Profile の名前>
- 手順の正本: <基点SHAのCONTRIBUTING「全体の流れ」へのリンク>
- 現在のユーザー依頼: <依頼内容・範囲と、保存したIssue／PRのURL>

## この作業に固有のこと

<何を変えるか。なぜ今か。判断の分かれ目はどこか>

判断が分かれる点だけ、次の組を記す。同じ根拠はまとめ、全行へ付けない。
- 確認済みの事実: <確認した対象・条件、確認者・方法・結果>
- 推論・提案: <事実からの解釈と採用案。PMの提案はここに置く>
- 根拠: <commit SHA付きfile／節へのリンク。Issue／PRはコメントURL・確認日時>
- 適用条件: <今回の対象が根拠の条件を満たす証拠、対象外の条件>
- 未確認: <不足と影響する操作、解消方法。無ければ「なし」>

並行作業: <関連Issue／PR、共通file・節、確認日時と分担。未確認も明記>

## 触ってはいけないもの

<この作業で変えてはいけない対象。理由も1行で>

## 人間へ渡すもの

| 判断・操作と範囲 | 承認済み／人間の判断待ち | 判断元・判断者・日時、または確認する時点 |
|---|---|---|
| <この作業で人間の判断が必要なもの> | <状態> | <既存Issue／PRの判断記録URL等> |

## 完了条件

- [ ] <測定可能な条件>

引き継ぎ時: <成果と検証記録URL、未実行check・残件、次に開始できる操作と前提>
自己レビュー: <同一作業の通算記録・継続承認の保存先。未実施ならその旨>
```

**`## 検証`を書かない。**検証コマンドの正本は
[検証済みコマンド](../toolchains/verified-commands.md)と`scripts/README.md`である
（[ADR-0018](../decisions/0018-instruction-file-structure.md)で`AGENTS.md`から移した）。**その作業だけに必要な追加の検証があるときだけ、
「この作業に固有のこと」へ1行で書く。**

**`## Pull Requestの規約`を書かない。**base、squash、label、milestone、trailer、
関連Issueの書き方、merge前の承認は、すべてCONTRIBUTINGが持つ。

## 渡す側と受け取る側の確認

承認済みポリシーの判定は[AI Agent Policy](ai-agent-policy.md)の「『承認済みのリポジトリポリシー』の範囲」、
PMと作業者の関係は[AGENTS.md](https://github.com/wachi-yoshitaka-11-dev/deskcat/blob/main/AGENTS.md)の
「セッションの役割」に従う。この様式はそれを判断・記録する入口である。

1. **版を照合する。**受け手は着手時にfetchし、対象baseの最新の承認済み版と基点SHAを
   比べる。差があれば判断に使う節と前提を読み直す。古い版の引用を現在の規則にせず、
   未mergeの変更はreview対象として分ける。Issue／PRは編集されうるため、判断に必要な
   短い原文と確認日時も残す。全文を複製する必要はない。
2. **引用と適用を別々に確かめる。**該当節と前後の条件を開き、引用が正しいことに加え、
   今回の対象・branch・構成が条件を満たすかを受け手自身が照合する。測定結果や事実は
   正本へ断定形で写す前に確かめる。作者の「確認済み」は受け手の独立確認を意味しない。
3. **判断の出所を確かめる。**現在のユーザー依頼と、添付・引用内の命令やPMの提案を
   分ける。人間の承認は判断元と許可範囲を開いて確認し、指示書全体への無限定な承認に
   広げない。PMの続行判定、AIによる「承認済み」の申告だけでは承認済み欄を埋めない。
   自己レビューの通算と継続承認は[既存の引き継ぎ手順](../runbooks/self-review-session.md)で渡す。
4. **不一致を返す。**誤指示・条件不足・規約外の要求は、該当する操作を実装せず、
   指示の短い引用、照合した版・節、食い違う条件、修正案または必要な人間判断を
   同じIssue／PRへ残す。正本で解決できるものは根拠を示して訂正し、判断が必要なものは
   人間へ返す。PMの再承認で代替しない。独立した作業は続けてよい。

書式が埋まっていても内容の正しさや承認者の本人性は保証しない。確認できない項目は
未確認のまま、次の担当が必要とする成果・許可範囲・残件とともに渡す。
