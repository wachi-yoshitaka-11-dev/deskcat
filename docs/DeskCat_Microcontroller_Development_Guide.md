## 0. この文書の目的

この文書は、参照資料の内容を DeskCat の実開発へ適用するために再構成した技術ガイドである。単なる記事の章別要約ではなく、次の用途を想定している。

- ESP32 の回路・ピン・電源設計を確定する
- Rust／ESP-IDF ファームウェアを段階的に実装する

- Raspberry Pi Zero WH との USB シリアル通信を安定化する
- AI コーディングを使いながら、誤推定・回帰・危険な自動操作を防ぐ
- 実機不具合をログ、計測器、デバッガで切り分ける
- 将来の部品変更や OTA に耐える構造を作る

本書の数値例や構造案は、次の三段階で区別する。

## 1. 最初に守るべき原則

DeskCat のマイコン開発では、以下を最上位のルールとする。

1. 要求、制約、受け入れ条件は人間が決める。
2. 部品仕様は販売ページや AI 回答ではなく、メーカーのデータシートで確認する。
3. GPIO、電源、通信、機械可動域は、実機確認前に推測で固定しない。
4. ハードウェア単体、デバイス単体、通信単体を先に検証し、最後に統合する。
5. 一度に完成品を生成させず、小さい実装と実測を積み重ねる。
6. 「動いた」だけでなく、観測可能なログ、カウンタ、状態取得手段を用意する。
7. ISR は短く保ち、重い処理はタスクまたはメインループへ渡す。
8. サーボは ESP32 から給電しない。外部電源を使い、GND を共通化する。
9. サーボ角度、速度、加速度、連続動作時間にソフトウェア上の安全制限を設ける。
10. Raspberry Pi と ESP32 の責務を混ぜない。
11. AI の修正後は、対象機能だけでなく既存機能の回帰も確認する。
12. AI が生成した低レベル初期化コードを、公式 SDK の初期化より先に信用しない。
13. ビルド、書き込み、ログ取得、テストの手順を CLI で再現可能にする。
14. 不具合解析では、仮説より先に完全なエラー、再現条件、ログ、波形を集める。
15. 未確定事項を暗黙の仮定で埋めず、TBD として管理する。

## 2. 参照資料から得られる中心的な知見

### 2.1 第一部から得られる知見

第一部の中心は、IoT 機器を AI と開発するときの要求定義、部品選定、段階実装、実機検証である。

- AI は候補比較、文書化、コード生成を高速化できる。
- 一方で、存在しない製品仕様、誤った型番解釈、古い情報、都合のよい同意を返すことがある。
- 公式資料を渡しても、最終的な型番、外形、電圧、精度、供給性、価格は人間が確認する必要がある。
- センサ、通信、統合を一度に実装せず、単体デモを先に作る。
- センサ値が不正な場合、回路、基準電圧、ADC、ライブラリ制限、ソフトウェア補正を段階的に切り分ける。
- 通信は既知のダミーデータで先に検証し、同期、長さ、CRC、連番、再構成、欠落を観測可能にする。
- 複数 AI のレビューは有効だが、ある修正で過去の補正が消えるなどの回帰も発生する。
- 正式仕様、決定記録、受け入れテストを一つの基準として維持する必要がある。

DeskCat では、この考え方を「LCD 単体」「入力単体」「サーボ単体」「Pi–ESP32 通信単体」「統合」の順序へ置き換える。

### 2.2 第二部から得られる知見

第二部の中心は、AI エージェントのリスク、OTA、実機デバッグ、GUI、センサ抽象化である。

- AI エージェントはファイル編集、コマンド実行、ライブラリ導入まで行えるため、最小権限と監査が必要である。
- 追加するスキル、ルール、プラグイン自体に悪意ある指示が含まれる可能性がある。
- デバッグ時は、ボード、OS、ツールチェーン、完全なエラー、期待値、実測値、再現条件を AI に渡す。
- AI が仮説を出し、人間が証拠を取得し、人間が採否を決める流れが有効である。
- OTA は A/B スロット、署名、検証、失敗時ロールバック、電源断耐性まで含めて設計する。
- メモリやフラッシュのセクタ構造といった実ハード制約は、一般論だけでは解決できない。
- 初期化順序やデバイス依存関係を設定へ明示すると、統合時の競合を減らせる。
- GUI は PC 上のシミュレーションだけで完了せず、実 LCD の色、フォント、座標、応答を確認する。
- センサ固有処理をアダプタへ閉じ込め、上位層には共通の測定値、状態、エラーを見せる。

DeskCat では、OTA は初期 MVP の必須機能ではない。ただし将来導入する場合に、単純な上書き更新で済ませないための設計知識として保持する。

### 2.3 別冊付録から得られる知見

別冊付録の中心は、IDE や HAL の下で起きているマイコン動作を理解し、CLI とデバッガで観測することである。

- SoC は CPU、ROM、RAM、周辺回路で構成される。
- 周辺回路は、CPU からメモリマップド・レジスタとして操作される。
- アプリ実行前に、スタック、`.data`、`.bss`、クロック、ピン、周辺回路を初期化する必要がある。
- コンパイラ、アセンブラ、リンカ、変換ツール、書き込みツール、デバッガの役割を理解すると、IDE 外でも原因を追える。
- LED、UART、I2C、SPI、割り込みの順で小さく立ち上げる方法が有効である。
- GPIO はモードだけでなく、プル、駆動、初期値、代替機能、割り込み条件まで設計する。
- UART 受信はリングバッファ、割り込み処理は最小限、重い処理は通常コンテキストで行う。
- リンカ・マップとサイズ情報は、コードや静的データがどこへ配置されたかを示す。
- GDB、OpenOCD、UART ログは競合する手段ではなく、相互補完する。

ただし、別冊の具体例は STM32／Cortex-M を中心としている。DeskCat の ESP32-DevKitC-32E はアーキテクチャ、ブート、割り込み、SDK が異なるため、レジスタ番地、ベクタ・テーブル、スタートアップ・コード、STM32 用設定をそのまま流用してはならない。

## 3. DeskCat のシステム境界

### 3.1 確定している役割分担

| 装置 | 主な責務 |
|---|---|
| ESP32-DevKitC-32E | LCD 描画、サーボ制御、タッチ検出、加速度取得、環境センサ取得、即時の安全制御 |
| Raspberry Pi Zero WH | 感情・状態モデル、自律動作方針、独り言生成、ログ保存、API、長期的な判断 |
| USB シリアル | ESP32 と Raspberry Pi 間の初期通信経路 |

この分担から、ESP32 は「実時間 I/O コントローラ」、Pi は「高水準の行動・状態コントローラ」と考える。

### 3.2 ESP32 に置くべき処理

- サーボ PWM の生成
- サーボの絶対的な角度・速度・加速度制限
- タッチ、加速度、環境センサの取得
- 入力のデバウンス、一次フィルタ、異常値除外
- LCD の描画プリミティブと描画状態
- Pi から来た命令の構文・範囲検証
- 通信断時の安全状態
- ウォッチドッグへの応答
- ハードウェア自己診断と状態報告

Pi が不正な角度や過大な速度を指示しても、ESP32 側で拒否または制限する。安全境界を Pi のアプリケーションだけに依存させない。

### 3.3 Raspberry Pi に置くべき処理

- 感情値や人格状態の更新
- 行動パターンの選択
- 長時間の履歴と学習用ログ
- API や外部サービスとの通信
- 複雑な文章生成
- ユーザー設定の永続管理
- ESP32 の状態をまとめた運用監視

### 3.4 二重実装を避ける

たとえば「撫でられたら喜ぶ」は次のように分ける。

1. ESP32 がタッチをデバウンスして `touch.pet` イベントを発行する。
2. Pi が感情状態を更新し、表情と首動作を決定する。
3. Pi が `face.set` と `servo.move` を送る。
4. ESP32 が範囲を検証し、LCD とサーボへ反映する。
5. ESP32 が結果または拒否理由を返す。

入力の意味付けと人格判断は Pi、安全な実行は ESP32 という境界を維持する。

## 4. 要求をハードウェア仕様へ落とす

### 4.1 要求表

実装前に、各機能を次の形式で確定する。

| 機能 | 入力 | 出力 | 期限・周期 | 失敗時 | 受け入れ条件 |
|---|---|---|---|---|---|
| 表情表示 | Pi の表情命令 | LCD | TBD | 直前の安全な表情を維持 | 指定パターンが実機表示される |
| 撫で検出 | タッチ | イベント | TBD | 未検出として扱う | 誤検出率と検出率が基準内 |
| 衝撃検出 | 加速度 | イベント | TBD | センサ異常を通知 | 指定試験で一度だけ通知 |
| 首動作 | Pi の動作命令 | サーボ | TBD | 中立または停止 | 可動域を越えず滑らかに動く |
| 環境測定 | 温湿度等 | 測定値 | TBD | stale／error を通知 | 基準計との差が許容内 |
| 状態通信 | 各状態 | JSON Lines | TBD | 再接続・再同期 | 欠落を検出できる |

周期やしきい値は、ユーザー体験、部品仕様、CPU 負荷、通信量を見て決める。AI に一般値を入れさせて確定扱いにしない。

### 4.2 品質要求

機能要求だけでなく、次も明記する。

- 起動時間
- 通信断からの復帰時間
- 電源再投入後の状態
- 連続稼働時間
- サーボ動作中の再起動有無
- センサ故障時の縮退動作
- LCD 更新中の入力取りこぼし
- 設定破損時の既定値復旧
- ファームウェアのバージョン識別
- ログ量と保存方針
- 将来の部品変更可能性

### 4.3 受け入れ条件は測定可能にする

悪い例:

- 反応が速い
- 滑らかに動く
- 通信が安定している

良い形式:

- 入力イベント受信から表情命令受付までの 95 パーセンタイルが `TBD ms` 以下
- サーボ目標値の更新間隔に `TBD ms` を超える停止がない
- `TBD 時間` の連続試験で再起動が 0 回
- シリアルの欠番、再送、パース失敗数を取得できる

値自体は試作後に確定してよいが、測り方は先に決める。

## 6. 電源と信号の基礎

### 6.1 電源系を信号系より先に設計する

DeskCat はサーボを含むため、電源設計が最優先である。サーボの急な電流変化は、ESP32 のブラウンアウト、LCD の乱れ、I2C エラー、シリアル切断の原因になり得る。

**確定事項:**

- サーボは外部 5 V 系から給電する。
- ESP32 の 3.3 V ピンや GPIO からサーボへ給電しない。
- ESP32、サーボ電源、各モジュールの GND は共通化する。

**要設計:**

- 5 V 電源の連続電流とピーク電流
- ESP32 側電源とサーボ側電源の分岐
- 逆流防止
- バルク・コンデンサとデカップリング
- 電源投入・切断順序
- USB 給電と外部給電を同時使用する場合の経路

### 6.2 電流予算

電源容量は平均電流だけで選ばない。

```text
必要連続電流 >= 各機器の最大連続電流の合計 × 設計余裕
必要ピーク電流 >= 同時に発生し得るピーク電流の合計
```

サーボは無負荷動作電流ではなく、起動、加速、拘束に近いピークを確認する。LCD バックライト、Wi-Fi 送信、センサヒータがある場合もピークを含める。

電圧降下の一次見積りには次を使える。

```text
ΔV ≈ I × Δt / C
```

ただし、実際には電源内部抵抗、配線抵抗、コンデンサ ESR、負荷波形が影響する。最終判断はオシロスコープで ESP32 入力電圧と 5 V 系を同時観測して行う。

### 6.3 デカップリングと配線

- 各 IC の電源ピン近傍に、データシート指定のデカップリングを置く。
- サーボの大電流経路をセンサ GND 経路と可能な範囲で分離し、電源入口付近で合流させる。
- 電源と GND の線を細く長くしない。
- I2C、SPI、PWM をサーボ電源線と長距離平行に走らせない。
- 試作配線でも、信号と GND の戻り経路を意識する。
- コネクタの抜き差し、逆接、半挿しを想定する。

### 6.4 ロジック電圧

ESP32 側の信号を原則 3.3 V 系として扱い、5 V 信号を直接入力しない。各端子の許容電圧は採用ボードの公式資料で確認する。

確認事項:

- モジュールの信号電圧
- モジュール基板のプルアップ先
- 双方向信号のレベル変換方式
- 起動前に相手側だけ給電される場合の逆流
- 未給電デバイスの入力保護ダイオード経由電流

### 6.5 ノイズと安全

- サーボ制御値に上限、下限、最大変化率を設ける。
- 起動中はサーボ信号を安全状態に保つ。
- GPIO を出力に切り替える前に、安全な出力ラッチ値を準備する。
- LCD リセット、バックライト、サーボ PWM は起動時グリッチを確認する。
- 外部に触れる端子や長いケーブルには ESD／過電圧対策を検討する。
- 機械的ストッパへ押し付け続けない。

## 7. GPIO 割り当て

### 7.1 割り当て前に全端子を棚卸しする

部分ごとに GPIO を決めると、最後に衝突する。次を一度に表へ載せる。

- LCD の SPI、CS、DC、RESET、BACKLIGHT
- タッチ・コントローラの SPI／I2C、CS、IRQ
- 加速度センサの I2C／SPI、IRQ
- 環境センサの I2C、任意の IRQ
- サーボ PWM
- USB-UART／書き込み／ログ
- ブートストラップ端子
- 開発ボード上で予約済みの端子
- 内蔵フラッシュ等が使用する端子
- 将来拡張端子

### 7.2 GPIO 管理表

```markdown
| GPIO | 開発ボード端子 | 用途 | 方向 | 起動時状態 | Pull | 速度/駆動 | 共有 | 制約 | 根拠 |
|---|---|---|---|---|---|---|---|---|---|
| TBD | TBD | LCD SCLK | Out | Low/TBD | None | TBD | SPI bus | boot制約確認 | 回路図 p.xx |
```

各行に根拠資料を記録する。AI が生成した表だけでは根拠にならない。

### 7.3 起動端子と予約端子

ESP32 には起動モードや内蔵機能に関係する端子がある。外部回路のプルアップ／プルダウンが起動条件へ影響しないかを確認する。

チェック:

- リセット直後に外部回路が端子を駆動しないか
- 書き込みモードに入れなくならないか
- 起動ログ用 UART と競合しないか
- 開発ボード上の USB-UART 回路と衝突しないか
- 入力専用または機能制限のある端子でないか

### 7.4 ピン競合をテスト可能にする

GPIO 表だけでなく、ファームウェアの設定にも単一の定義元を作る。

- ピン番号を各ドライバへ直書きしない
- ボード設定モジュールへ集約する
- 同じ GPIO の二重割り当てをビルド時または起動時に検出する
- 起動ログへ最終割り当てを出す
- 回路リビジョンをファームウェア設定と対応付ける

## 8. マイコン内部で起きていること

### 8.1 SoC の構成

一般的な SoC は次を含む。

- CPU コア
- ROM とフラッシュ
- SRAM
- 割り込みコントローラ
- クロック、リセット、電源管理
- GPIO
- UART、I2C、SPI
- タイマ、PWM
- ADC などの周辺回路
- ウォッチドッグ
- 無線機能

CPU は周辺回路を専用命令だけでなく、特定アドレスのレジスタへの読み書きとして操作する。このため、誤ったアドレス、クロック未供給、ピン機能未設定、初期化順序の誤りがあると動作しない。

### 8.2 リセットからアプリまで

概念的には次の順で動く。

1. リセット要因を受ける。
2. ROM ブートローダが起動する。
3. フラッシュ上のブートローダ／アプリを検証・ロードする。
4. スタックと実行環境を準備する。
5. 初期値付き静的データを RAM へ配置する。
6. ゼロ初期化領域をクリアする。
7. CPU、クロック、メモリ、SDK を初期化する。
8. ドライバ、タスク、アプリを開始する。

Rust／ESP-IDF では大部分をフレームワークが担う。理解は必要だが、初期段階から独自スタートアップやレジスタ直接操作へ置き換える理由にはならない。

### 8.3 メモリ領域

一般的な実行ファイルには次の領域がある。

| 領域 | 内容 | 注意点 |
|---|---|---|
| `.text` | 命令 | フラッシュ容量、実行位置 |
| `.rodata` | 定数、文字列 | 大量ログ文字列や画像で増える |
| `.data` | 初期値付き静的変数 | フラッシュと RAM の両方を使う |
| `.bss` | ゼロ初期化静的変数 | RAM を消費する |
| stack | 関数呼出し、局所変数 | タスクごとの深さ不足に注意 |
| heap | 動的確保 | 断片化、失敗処理、長期安定性 |

DeskCat では画像素材、描画バッファ、JSON バッファ、タスク・スタックが RAM を大きく消費し得る。ビルド結果のサイズと、実行時の最小空きヒープを監視する。

### 8.4 リンカ・マップ

リンク時の map ファイルやサイズ表示で確認する。

- どのオブジェクトがフラッシュを消費しているか
- 大きい静的バッファがどこにあるか
- 不要コードが除去されているか
- 画像やフォントが意図した領域にあるか
- デバッグ版とリリース版の差

原因不明の容量超過を、ライブラリを無作為に削ることで直さない。まず map と size を見る。

### 8.5 クロック

CPU、周辺回路、通信速度、PWM はクロックに依存する。

- CPU クロック
- APB 等の周辺バス・クロック
- UART ボーレート
- I2C／SPI クロック
- PWM 周期と分解能
- RTOS tick と高分解能タイマ

クロック設定を変えると、複数の周辺機能へ影響する。サーボ周期だけを直すつもりでシステム全体の時間基準を変更しない。

### 8.6 リセット要因

起動時に少なくとも次を識別してログへ出す。

- 電源投入
- 外部リセット
- ソフトウェア・リセット
- ウォッチドッグ
- ブラウンアウト
- パニック／例外後の再起動
- OTA や更新に伴う再起動

再起動回数と直前の異常状態を Pi へ報告できるようにする。

## 9. ESP32／Rust／ESP-IDF の開発方針

### 9.1 採用方針

承認済みのproject方針に従い、初期候補は次とする。

- 言語: Rust
- ターゲット: ESP32-DevKitC-32E
- SDK: ESP-IDF 系
- HAL: `esp-idf-hal` 系
- 実行環境: `std` 利用可能な ESP-IDF 構成
- 描画: 初期 MVP は単純な図形描画を優先

正確な Rust ツールチェーン、ESP-IDF、crate のバージョンは実装開始時に公式資料で組み合わせを確認し、ロックファイルと開発手順へ固定する。

### 9.2 HAL を使う理由

HAL は次を提供する。

- 端子と周辺回路の型安全な所有
- 公式 SDK の初期化経路
- GPIO、SPI、I2C、PWM の共通化
- RTOS やドライバとの整合
- レジスタ直接操作より保守しやすい API

HAL に問題がある場合も、いきなり全面的なレジスタ直書きへ移行しない。

1. 完全なエラーと条件を取得する。
2. 公式 SDK の制約を確認する。
3. ドライバ・ログを増やす。
4. 最小再現コードを作る。
5. 必要な箇所だけ低レベル API を検討する。

`unsafe` は原則禁止とし、不可避な場合はスコープ、根拠、不変条件、テストを明記してレビューする。

### 9.3 所有権と共有資源

Rust の所有権は、同じ SPI や I2C を複数ドライバから無制御に触る問題を防ぐ助けになる。ただし共有バスは明示的に設計する。

- バス所有者を一つにする
- 各デバイス設定を分離する
- 排他区間を短くする
- ロック中に待ち時間の長い処理をしない
- ISR から通常の mutex を取得しない
- デバイスごとの SPI 速度やモード切替を保証する

### 9.4 推奨モジュール境界

```text
firmware/
├─ src/
│  ├─ main.rs
│  ├─ board/          # GPIO、バス、ボードリビジョン
│  ├─ drivers/        # LCD、touch、accelerometer、environment、servo
│  ├─ protocol/       # JSON Lines、型、検証、連番
│  ├─ tasks/          # input、display、motion、communication、health
│  ├─ domain/         # イベント、測定値、表情、動作
│  ├─ diagnostics/    # ログ、カウンタ、自己診断
│  └─ config/         # 安全範囲、周期、校正値
├─ tests/
├─ scripts/
└─ docs/
```

実際のディレクトリ名はリポジトリ作成時に決めるが、ハードウェア依存コード、プロトコル、ドメイン判断を混在させない。

### 9.5 設定値

次はコードへ散在させず、型付き設定として集約する。

- GPIO
- I2C／SPI 速度
- デバイス・アドレス
- LCD の寸法と向き
- タッチ座標変換
- サーボ最小・中立・最大
- サーボ最大速度・加速度
- 入力デバウンス
- 加速度イベントしきい値
- センサ取得周期
- 通信タイムアウト
- 最大メッセージ長

安全に関係する値には、設定ファイルで変更可能な範囲そのものにも上限を設ける。

## 10. 割り込み、タスク、イベント

### 10.1 ISR の責務

割り込み処理で行うこと:

- 割り込み要因を確認・解除する
- 必要最小限の値または時刻を取得する
- イベントまたはフラグをキューへ渡す
- オーバーランをカウントする

割り込み処理で行わないこと:

- JSON の生成や解析
- LCD の全画面描画
- I2C／SPI の長いトランザクション
- 動的メモリ確保
- ブロッキング待機
- 長いログ出力
- サーボ動作シーケンス
- 複雑なデバウンス

### 10.2 タスク分割の推奨

| タスク | 責務 | 主な入力 | 主な出力 |
|---|---|---|---|
| communication | Pi との送受信、パース、応答 | UART RX | コマンド、イベント送信 |
| input | タッチ、加速度、環境センサ | IRQ／周期タイマ | 正規化イベント、測定値 |
| display | 表情状態の描画 | 表情コマンド | LCD |
| motion | 軌道生成、安全制限 | 動作コマンド | PWM |
| health | WDT、統計、故障状態 | 各タスクの heartbeat | status、再初期化 |

タスク数を増やすこと自体が目的ではない。優先度逆転、ロック競合、スタック不足が起きない最小構成にする。

### 10.3 イベント駆動

上位層はデバイスの生データではなく、意味のあるイベントを扱う。

```text
TouchStarted
TouchContinued
TouchEnded
TapDetected
ImpactDetected
OrientationChanged
EnvironmentUpdated
SensorFault
CommunicationLost
```

生の割り込み一回をそのまま「撫でられた」と判断しない。時系列、継続時間、変化量、デバウンスを用いる。

### 10.4 デバウンス

入力ごとに状態機械を用意する。

```text
Idle
  └─ candidate detected → Candidate
Candidate
  ├─ stable for threshold → Active
  └─ disappeared → Idle
Active
  └─ released for threshold → Idle
```

しきい値は実測データから決める。ログへ raw 値、判定値、状態遷移時刻を出せるようにする。

### 10.5 ウォッチドッグ

- 各重要タスクが定期的に進行していることを確認する。
- 単に WDT を feed する専用タスクだけを動かさない。
- 再起動前に可能な範囲で原因を保存する。
- 起動後に WDT リセット回数を報告する。
- デバッガ停止中の WDT 挙動を理解する。
- 長い描画、センサ待ち、ログ出力でタスクが占有されないようにする。

## 11. UART／USB シリアル通信

### 11.1 初期方針

**確定している候補:**

- USB シリアル
- JSON Lines
- 115200 bps
- 最大 1 メッセージ 1024 bytes

115200 bps と 1024 bytes は候補値であり、実際のログ量、遅延、USB-UART、Pi 側実装を測定して確定する。

### 11.2 UART の基礎

一般的な UART は次を合わせる。

- ボーレート
- データ・ビット
- パリティ
- ストップ・ビット
- フロー制御

候補は 115200、8 data bits、no parity、1 stop bit、no flow control だが、両端で同じ設定を明示する。

非同期シリアルは、スタート・ビット、データ・ビット、任意のパリティ、ストップ・ビットで一文字を表現する。一般的な 8N1 では、1 byte の送信に概ね 10 bit を使う。

概算:

```text
実効 byte/s ≈ baud / 10
115200 bps の場合 ≈ 11520 byte/s
```

ここから JSON のオーバーヘッド、OS バッファ、ログ、応答を差し引く。大きな状態を高頻度に送らない。

### 11.3 JSON Lines の規則

- 1 行 1 JSON オブジェクト
- 改行はメッセージ境界
- 文字コードは UTF-8
- 送信途中の改行を文字列へ直接入れない
- 最大長を受信前に制限する
- 構文エラー行は破棄し、カウンタと理由を残す
- 未知フィールドは互換性方針に従う
- 同じポート上の全出力を JSON とし、通常ログで破壊しない

### 11.4 推奨エンベロープ

以下は実装案であり、プロトコル仕様書で確定する。

```json
{"v":1,"type":"cmd","name":"face.set","seq":101,"payload":{"expression":"happy"}}
{"v":1,"type":"ack","seq":101,"ok":true}
{"v":1,"type":"event","name":"touch.pet","seq":8801,"ts_ms":123456,"payload":{"duration_ms":640}}
{"v":1,"type":"status","seq":8802,"ts_ms":123500,"payload":{"uptime_ms":123500}}
{"v":1,"type":"log","level":"warn","code":"I2C_TIMEOUT","ts_ms":123510,"message":"environment sensor timeout"}
```

最低限必要な情報:

- プロトコル・バージョン
- メッセージ種別
- コマンド／イベント名
- 連番
- 単調増加時刻
- payload
- 成功／失敗
- 機械判定可能なエラー・コード

### 11.5 コマンド処理

コマンド受信時の順序:

1. 行長を確認する。
2. JSON 構文を検証する。
3. バージョンを確認する。
4. コマンド名を確認する。
5. 必須フィールドと型を確認する。
6. 値の範囲を確認する。
7. 安全制限を適用する。
8. 実行キューへ登録する。
9. 受付または拒否を応答する。
10. 必要なら完了イベントを返す。

「受付」と「動作完了」は異なる。サーボの長い動作は、即時 ACK と後続の完了イベントに分ける。

### 11.6 再送と冪等性

通信再接続や応答欠落に備える。

- `seq` で重複を検出する。
- `face.set` のような状態設定は冪等にする。
- 相対移動コマンドの再送は二重動作を起こすため、コマンド ID を記録する。
- Pi は timeout 後に無条件再送せず、状態照会または同一 ID で再試行する。
- ESP32 は直近に処理した ID と結果を短期間保持する。

### 11.7 再接続と状態同期

再接続時:

1. ESP32 が `hello` とファームウェア情報を送る。
2. Pi が対応プロトコルを確認する。
3. Pi が `status.get` を送る。
4. ESP32 が現在の LCD、サーボ、センサ、fault、uptime を返す。
5. Pi が望ましい状態を再送する。

再接続直後に、以前の相対動作コマンドを再実行しない。

### 11.8 受信実装

- 固定上限付きバッファを使う。
- 改行まで読み、上限超過時は次の改行まで捨てる。
- UTF-8 不正、JSON 不正、未知コマンドを別カウンタにする。
- 一部だけ届くことを前提にする。
- 複数行が一度に届くことを前提にする。
- RX 処理とコマンド実行を分離する。
- TX 詰まりでセンサや WDT を停止させない。

## 12. I2C

### 12.1 基礎

I2C は一般に SDA と SCL の 2 線を複数デバイスで共有する。オープンドレインのためプルアップ抵抗が必要である。

確認事項:

- 7-bit／10-bit アドレス
- 同一アドレスの競合
- 供給電圧とプルアップ先
- バス速度
- プルアップ抵抗
- 配線長とバス容量
- clock stretching
- repeated start の要否
- 起動後の待ち時間
- 変換完了待ち
- CRC

### 12.2 プルアップ

複数モジュールにプルアップが実装されていると、並列合成で抵抗値が小さくなり過ぎることがある。反対に、抵抗が大きすぎると立上りが遅くなる。

設計では I2C 仕様とデバイスの sink 電流、バス容量を使って範囲を決め、実機波形を確認する。モジュール上の抵抗値と接続先電圧を回路図または実測で確認する。

### 12.3 ドライバの読み出し

センサによって次が異なる。

- レジスタ・アドレス幅
- エンディアン
- 一回の読み出し長
- 連続読み出し可否
- 自動アドレス増加
- repeated start
- CRC 単位
- 測定開始コマンドと待ち時間

ライブラリのバッファ上限や、一度に読めるサイズも確認する。参照資料では、デバイス側が大きなデータを返せてもソフトウェア・ライブラリの上限により読み切れない事例がある。

### 12.4 タイムアウトと復旧

- 全トランザクションに timeout を設ける。
- NACK、timeout、CRC、not ready を区別する。
- 一時的失敗は回数制限付きで再試行する。
- SDA が Low 固着した場合の復旧方針を設ける。
- デバイス再初期化とバス再初期化を分ける。
- 連続失敗時は故障状態へ移し、他デバイスを巻き込まない。

### 12.5 検証順序

1. 電源と静止時電流を確認する。
2. SDA／SCL のアイドル電圧を確認する。
3. バス・スキャンまたは既知 ID レジスタを読む。
4. 最小速度で単発読み出しを行う。
5. raw byte をログする。
6. データシートの変換式を適用する。
7. 基準器と比較する。
8. 周期取得を行う。
9. サーボ動作中にもエラー率を測る。

## 13. SPI、LCD、タッチ

### 13.1 SPI の基礎

一般的な信号:

- SCLK
- MOSI
- MISO
- デバイスごとの CS

デバイスごとに異なる条件:

- SPI mode
- 最大クロック
- bit order
- word size
- CS setup／hold
- half／full duplex
- DMA 制約

### 13.2 バス共有

LCD とタッチが同じ SPI バスを共有できる場合でも、次を保証する。

- CS は個別にする。
- 同時に二つの CS を有効化しない。
- デバイス切替時に mode と速度を正しく設定する。
- LCD の長い DMA 転送がタッチ IRQ を長時間待たせない。
- MISO を使わないデバイスがバスを駆動し続けない。
- RESET、DC、BACKLIGHT、IRQ は個別管理する。

### 13.3 LCD の立ち上げ

1. 電源、ロジック電圧、バックライト経路を確認する。
2. RESET と BACKLIGHT の安全な起動状態を確認する。
3. 最小 SPI 速度で初期化する。
4. 単色塗りを表示する。
5. 四隅と座標軸が分かるテスト・パターンを表示する。
6. 回転、幅、高さ、色順を確定する。
7. 小さい矩形更新を行う。
8. 表情プリミティブを描く。
9. 実機のちらつき、色、フォント、更新時間を確認する。

PC 上のシミュレータは座標や状態遷移の確認には有効だが、実 LCD の色順、転送速度、アンチエイリアス、視認性は代替できない。

### 13.4 初期 MVP の描画方針

DeskCat は画像素材を使わない方針のため、次の図形を組み合わせる。

- 背景矩形
- 目の楕円、線、弧
- 口の線、弧
- 必要最小限の文字

利点:

- フラッシュ容量を抑えやすい
- 表情パラメータを補間しやすい
- 色や寸法をコードで一元管理できる
- 画像アセットのライセンス管理が不要

描画コマンドを直接プロトコルへ露出させず、`happy`、`surprised` などの表情状態を ESP32 内で描画へ変換する。

### 13.5 タッチ

タッチ方式によって、raw 値、座標、圧力、IRQ、校正が異なる。

確認事項:

- LCD 座標とタッチ座標の原点・向き
- 回転時の変換
- raw min／max
- 押下・解放しきい値
- ノイズとチャタリング
- 長押し、タップ、撫での分類
- LCD 更新中の読み出し遅延
- SPI 共有時の速度

参照資料には、タッチ IC の SPI クロックが高すぎて座標を取得できない事例がある。最大仕様だけでなく、モジュール、配線、ドライバを含む実動作速度を測定する。

### 13.6 タッチ座標の校正

少なくとも四隅と中央を用いて raw 座標から画面座標への変換を決める。

- 軸入替
- X／Y 反転
- オフセット
- スケール
- 必要ならアフィン変換

校正値には、対象ディスプレイ、回転、回路リビジョンを関連付ける。

## 14. 加速度センサ

### 14.1 目的を分ける

DeskCat で想定される用途:

- 軽いタップの検出
- 強い衝撃の検出
- 傾きまたは転倒の検出
- サーボ動作に伴う自己振動の把握

同じ加速度値でも用途ごとに帯域、しきい値、継続時間が異なる。

### 14.2 raw 値からイベントまで

1. raw XYZ を取得する。
2. 感度設定に従って物理単位へ変換する。
3. オフセットを校正する。
4. 必要なフィルタを適用する。
5. 重力成分と動的成分を目的に応じて扱う。
6. 大きさ、差分、時間窓を計算する。
7. ヒステリシス付きでイベントを判定する。
8. 再トリガ抑制を行う。

例:

```text
magnitude = sqrt(x² + y² + z²)
dynamic = |magnitude - gravity_reference|
```

これは考え方の例であり、しきい値はセンサ・レンジ、設置方向、筐体、サーボ振動の実測から決める。

### 14.3 自己振動との区別

サーボ動作中は加速度イベントが誤発火し得る。

選択肢:

- サーボ動作状態を判定器へ入力する
- サーボ固有の周波数帯をフィルタする
- イベントしきい値を状態に応じて変える
- サーボ指令と加速度時系列をログし、特徴を比較する

イベントを全面的に無効化すると本当の衝撃も見逃すため、実測に基づいて設計する。

### 14.4 校正と試験

- 静止状態を複数姿勢で測る
- 分散、温度変化、個体差を記録する
- 指定の軽いタップを繰り返す
- 机の振動、キーボード、歩行振動を試す
- サーボの全動作パターンを試す
- イベントの真陽性、偽陽性、見逃しを集計する

## 15. 環境センサ

### 15.1 共通測定モデル

上位層へは raw レジスタではなく、測定値と品質を返す。

```rust
struct Measurement<T> {
    value: T,
    timestamp_ms: u64,
    quality: MeasurementQuality,
}

enum MeasurementQuality {
    Valid,
    Stale,
    NotReady,
    OutOfRange,
    SensorFault,
}
```

これは設計例であり、実装時に Rust の型とシリアライズ方針を確定する。

### 15.2 センサ固有処理を閉じ込める

ドライバ内部:

- レジスタ操作
- 測定開始
- 変換待ち
- CRC
- 校正係数
- raw 値の変換
- センサ固有エラー

上位層:

- 物理量
- 単位
- 測定時刻
- freshness
- 共通エラー

### 15.3 ブロッキングを避ける

測定に長い待ち時間があるセンサは、上位要求のたびに同期測定しない。

推奨:

1. センサ・タスクが周期的に測定を開始する。
2. 完了後に結果をキャッシュする。
3. 上位層は最新値と時刻を読む。
4. 古い場合は `Stale` を明示する。

### 15.4 共通ライフサイクル

将来の部品交換を考え、概念的に次を揃える。

```text
open → configure → start → read/update → stop → close
```

単純なセンサに不要な段階があっても、最も複雑な候補を基準にインターフェースを検討する。ただし抽象化を先に作り過ぎず、異なる二種類目の実装で妥当性を確認する。

### 15.5 エラー分類

- Bus
- Timeout
- Checksum
- NotReady
- OutOfRange
- InvalidCalibration
- UnsupportedConfiguration
- DeviceIdentityMismatch

ログには共通分類と、デバッグ用のセンサ固有詳細を残す。

## 16. サーボ制御

### 16.1 電気的前提

- サーボ電源は外部 5 V 系とする。
- ESP32 とサーボ電源の GND を共通化する。
- PWM 信号レベルの適合性をサーボ仕様で確認する。
- 起動・停止・拘束時の電流を確認する。
- 電源電圧降下を ESP32 側と同時観測する。

### 16.2 PWM

一般的なホビーサーボには周期的なパルス幅制御が使われるが、周期、最小／中立／最大パルス幅は製品ごとに確認する。

変換の概念:

```text
commanded_angle
  → mechanical clamp
  → speed/acceleration limiting
  → calibrated pulse width
  → hardware PWM
```

「0–180 度」「1–2 ms」などの一般値を、採用サーボの確定値として使わない。

### 16.3 必須の安全制限

- ソフト最小角
- ソフト最大角
- 中立角
- 最大角速度
- 最大角加速度
- 一回の最大動作量
- 連続動作時間
- 通信断時の動作
- センサ／電源異常時の動作

機械可動域は、サーボ単体の仕様より筐体の干渉で狭くなることがある。低速・小範囲から実機校正する。

### 16.4 軌道生成

Pi から目標角だけを受け、ESP32 が一定周期で補間する構造を推奨する。

- step 変化をそのまま PWM へ入れない
- 最大変化量を時間基準で制限する
- 滑らかさが必要なら加減速を設ける
- 新しい命令で軌道を置き換える規則を決める
- 停止と中立復帰を別コマンドにする

### 16.5 フェイルセーフ

通信断時の選択肢:

- 現在位置を一定時間保持後、PWM を停止
- 低速で中立へ戻して停止
- 現在位置を保持

どれが安全かは機構とサーボ特性による。無通電時に首が落下するか、PWM 停止で保持力が失われるかを実機確認して決める。

### 16.6 試験

1. サーボを機構から外して信号を確認する。
2. 狭いパルス範囲で動作確認する。
3. 電源電流と電圧を測る。
4. 機構へ取り付け、狭い角度から広げる。
5. 左右端の機械余裕を記録する。
6. 速度・加速度を段階的に上げる。
7. LCD、I2C、シリアルを同時動作させる。
8. 通信断、再起動、電源断を試す。

## 17. ADC とアナログ計測

初期 DeskCat に ADC 利用が含まれるかは未確定だが、電源監視や将来センサで必要になる可能性がある。

### 17.1 ADC 値をそのまま電圧とみなさない

確認事項:

- 分解能
- 有効範囲
- 減衰／入力レンジ設定
- 基準電圧と個体差
- 入力インピーダンス
- 非直線性
- 校正 API
- サンプリング時間
- 無線動作との干渉

### 17.2 推奨手順

1. raw code を保存する。
2. 既知の 2 点以上を基準器で測る。
3. 公式校正機能を確認する。
4. offset と gain を分けて扱う。
5. 複数サンプルの平均、中央値、外れ値除去を比較する。
6. 必要なら RC ローパスを設計する。
7. サーボ停止時と動作時を比較する。

参照資料の重要な教訓は、基準電圧を思い込みで固定すると、補正コード全体が誤ることである。必ず採用 MCU と回路で確認する。

## 18. ドライバ抽象化

### 18.1 抽象化の目的

抽象化はコードを美しく見せるためではなく、次に備えるために行う。

- センサ供給停止
- 別メーカーへの変更
- 同時比較評価
- シミュレータや fake 実装
- 故障注入テスト

### 18.2 共通化するもの

- 測定対象の物理量
- 値と単位
- 時刻
- freshness
- ライフサイクル
- 共通エラー

### 18.3 共通化し過ぎないもの

- 特定センサだけの自己診断
- 特殊測定モード
- ヒータ制御
- FIFO や割り込みの詳細
- 固有校正手順

固有機能は capability として分離し、最小共通 API を膨らませない。

### 18.4 実装手順

1. ドメイン型と最小インターフェースを作る。
2. 一つ目の実デバイスを実装する。
3. fake 実装で上位テストを書く。
4. 性質の異なる二つ目の候補で抽象化を検証する。
5. 必要な差だけ capability として追加する。

既知の一製品を暗黙に想定した「汎用」インターフェースにしない。

## 19. 段階的な立ち上げ計画

一度に全機能を統合しない。各段階で成果物、観測手段、合格条件を持つ。

### Phase 0: 設計資料を確定

成果物:

- 正式な部品表
- 回路図
- GPIO 表
- 電源予算
- プロトコル仕様
- 安全制限表
- テスト計画

合格条件:

- 全端子の用途と根拠が記録されている
- ロジック電圧が整合している
- サーボ電源経路が ESP32 から分離されている
- TBD が一覧化されている

### Phase 1: ビルドと書き込み

実装:

- 最小アプリ
- 起動ログ
- firmware version
- reset reason

合格条件:

- クリーン環境から CLI でビルドできる

- バージョンとリセット要因を取得できる

### Phase 2: UART／USB シリアル

実装:

- JSON Lines parser
- `hello`
- `ping`／`pong`

### Phase 3: GPIO と単純出力

合格条件:

### Phase 4: I2C とセンサ一個

実装:

- I2C 初期化

合格条件:

- 連続取得でエラー率を測定できる
- センサ切断を検出し、復旧または fault 化できる

### Phase 5: SPI と LCD

実装:

- 単色表示
- テスト・パターン
- 図形描画
- 最小表情

合格条件:

- 向き、色、座標が一致する

- 電源再投入で確実に初期化する

### Phase 6: タッチ

実装:

- raw 取得
- 座標校正
- 押下／解放
- 撫でイベント

合格条件:

- LCD 更新との同時動作で取りこぼしを測定できる
- 誤検出と見逃しが受け入れ基準内

### Phase 7: 加速度

実装:

- raw XYZ
- 校正
- フィルタ
- tap／impact イベント

合格条件:

- サーボ停止時と動作時の判定特性を記録する
- 再トリガ抑制が動作する

### Phase 8: サーボ単体

実装:

- 外部電源
- 狭い可動域
- PWM 校正
- 速度／加速度制限
- emergency stop

合格条件:

- 電圧降下で ESP32 が再起動しない
- 機械端へ衝突しない
- 通信断時に安全動作する

### Phase 9: 統合

統合順:

1. 通信 + LCD
2. 通信 + タッチ
3. 通信 + 加速度
4. 通信 + サーボ
5. 全センサ + LCD

各追加前後で、既存の受け入れテストを再実行する。

### Phase 10: 長時間・異常試験

- 最大頻度コマンド
- サーボ連続動作
- 低電圧に近い条件

## 21. 実機デバッグ

### 21.1 AI へ渡す情報

不具合報告には次を含める。

```text
目的:
期待動作:
実際の動作:
再現率:
再現手順:
ボードと回路リビジョン:
部品の正確な型番:
電源条件:
ツールチェーンと SDK:
変更したコミット:
完全なビルドエラー:
完全な起動ログ:
直前に試したこと:
測定した電圧／波形:
まだ試していないこと:
```

ログの一行だけを切り出すより、失敗前後を含む完全な流れを渡す。

### 21.2 仮説と証拠を分ける

```markdown
| 仮説 | 期待される証拠 | 確認方法 | 結果 | 判定 |
|---|---|---|---|---|
| サーボ電源降下 | 3.3 V低下と同時にbrownout | オシロ同時測定 | TBD | TBD |
| I2C pull-up過小 | Low電流過大、波形異常 | 抵抗実測・波形 | TBD | TBD |
```

AI の説明がもっともらしくても、証拠なしに確定しない。

### 21.3 切り分けの順序

1. 再現条件を固定する。
2. 直前の変更を確認する。
3. 電源と GND を測る。
4. 初期化結果と reset reason を確認する。
5. 最小構成で再現する。
6. 通信波形と raw byte を確認する。
7. ドライバの詳細ログを有効にする。
8. データシートの該当条件を読み直す。
9. 速度を下げる、転送を小さくする等で境界を探る。
10. 修正後に元の受け入れテストを再実行する。

参照資料の実例では、転送長の偶奇や初期化依存関係のような条件が、一般的な仮説では見つからず、詳細ログとデータシートで特定された。

### 21.4 計測器

#### デジタル・マルチメータ

- 電源電圧
- 配線導通
- 抵抗値
- 静止電流

#### オシロスコープ

- サーボ動作時の 5 V／3.3 V
- 起動時電源波形
- PWM パルス幅
- I2C 立上り
- SPI クロックと CS
- リセット信号

#### ロジック・アナライザ

- UART byte
- I2C アドレス、ACK、データ
- SPI mode、CS、転送内容
- タイミング関係

計測器の GND 接続で短絡しないよう、測定対象の基準と機器の接地を確認する。

### 21.5 デバッガ

デバッガで確認できること:

- breakpoint
- backtrace
- 変数
- メモリ
- レジスタ
- task 状態
- fault 発生位置

注意:

- 停止中もサーボや外部機器は動作し得る。
- デバッガ停止で WDT が発火する場合がある。
- タイミング依存不具合は breakpoint で消えることがある。
- デバッガだけでなく UART ログと波形を併用する。

ESP32 で利用する具体的な JTAG、GDB、OpenOCD 系手順は、採用ボードと ESP-IDF の対応版に合わせて別途確定する。

## 23. テスト戦略

### 23.1 テスト層

| 層 | 対象 | 実行場所 |
|---|---|---|
| unit | パーサ、変換、状態機械、範囲制限 | PC |
| property／fuzz | JSON、入力境界、重複、任意 byte | PC |
| integration | タスク間、fake driver、プロトコル | PC／ESP32 |
| driver | 実センサ、LCD、PWM | ESP32 実機 |
| HIL | Pi–ESP32、電源断、切断、連続動作 | 結合環境 |
| acceptance | ユーザー行動と MVP シナリオ | 完成試作 |

### 23.2 PC 上でテストするもの

- JSON Lines の分割・結合
- 最大長境界
- 不正 UTF-8／不正 JSON
- 未知フィールド
- 連番の欠落・重複
- サーボ clamp
- 軌道計算
- タッチ状態機械
- 加速度イベント状態機械
- stale 判定
- エラーからの状態遷移

ハードウェア依存部分を trait／adapter で分離すると、PC で高速に回帰試験できる。

### 23.3 実機でしか確認できないもの

- 電源品質
- GPIO 起動状態
- I2C／SPI 波形
- LCD の見え方
- タッチ座標
- 加速度ノイズ
- サーボ可動域と負荷
- 無線やサーボによる干渉
- 実時間性
- 長時間メモリ安定性

### 23.4 故障注入

- センサを外す
- CRC 不正を fake で返す
- timeout を発生させる
- JSON を途中で切る
- 最大長を超える
- Pi を再起動する
- ESP32 を再起動する
- USB を抜き差しする
- コマンドを重複させる
- キューを意図的に満たす
- サーボ命令を範囲外にする

故障時に「止まらない」だけでなく、故障を観測し、安全に縮退し、復旧できることを確認する。

### 23.5 MVP シナリオ

#### 表情

1. 起動する。
2. LCD が既定表情を表示する。
3. Pi から `happy` を送る。
4. ESP32 が ACK する。
5. 実 LCD が happy 表情になる。

#### 撫で

1. タッチ raw 値を取得する。
2. 撫で操作を行う。
3. 一回の意味イベントを送る。
4. Pi が happy を決める。
5. LCD と首動作が安全に実行される。

#### 軽い衝撃

1. 規定の軽い tap を与える。
2. 加速度イベントを一度送る。
3. Pi が surprised を決める。
4. 誤った連続イベントが出ない。

#### 通信断

1. 動作中に USB を切断する。
2. ESP32 が安全状態へ移る。
3. 再接続後に hello／status 同期する。
4. 古い相対動作を再実行しない。

## 24. GUI／表情実装

### 24.1 開発ループ

```text
表情仕様
  → 描画コード
  → PCシミュレーション
  → ESP32ビルド
  → 実LCD表示
  → 目視・計測
  → 修正
```

PC のスクリーンショット比較は有効だが、最終判断は実 LCD で行う。

### 24.2 表情を状態として定義する

表情名だけでなく、描画パラメータを構造化する。

```text
FaceState
  eye_shape
  eye_open
  eye_offset
  mouth_curve
  mouth_open
  color_scheme
  transition_duration
```

MVP では必要最小限にし、過度な汎用 GUI フレームワーク導入を避ける。

### 24.3 部分更新

全画面更新と部分更新を比較する。

- 転送時間
- ちらつき
- 実装複雑性
- タッチ待ち時間
- RAM 使用量

部分更新を行う場合、前フレームの消去、重なり、dirty rectangle の漏れをテストする。

## 25. OTA を将来導入する場合

初期 MVP は USB 書き込みを優先する。OTA を追加する場合は、単にネットワークから受け取ったバイナリを上書きしない。

### 25.1 必要要素

- 更新クライアント
- 配布サーバ
- 署名済みイメージ
- デバイス上の署名検証
- A/B または同等の復旧可能なパーティション
- 更新状態管理
- 起動確認
- rollback
- 電源断耐性
- バージョン・ダウングレード方針

### 25.2 鍵管理

- 秘密署名鍵をデバイスへ入れない。
- 秘密鍵をリポジトリへ入れない。
- デバイスには検証に必要な公開情報だけを置く。
- CI／署名環境の権限を分離する。

### 25.3 更新シーケンス

1. manifest を取得する。
2. 対象ハードウェアとバージョンを確認する。
3. secondary slot へ書く。
4. hash と署名を検証する。
5. 次回起動先を更新する。
6. 再起動する。
7. self-test と Pi 通信を確認する。
8. 成功を確定する。
9. 失敗または timeout なら旧版へ戻す。

### 25.4 フラッシュ設計

パーティション容量だけでなく、erase sector、アラインメント、ブートローダ制約、NVS、ログ領域を確認する。参照資料では、内部／外部フラッシュのセクタ構成差により、想定した swap が成立しなかった事例がある。

## 26. 安全性とセキュリティ

### 26.1 実機安全

- サーボの機械可動域をハードとソフトで制限する。
- 初回試験は機構から外すか、狭い範囲で行う。
- 緊急停止手段を用意する。
- 手やケーブルの挟み込みを確認する。
- 異音、発熱、拘束時は直ちに電源を切る。
- 電源容量と配線温度を確認する。

### 26.2 入力検証

Pi は信頼できる同一装置内の相手でも、通信データは検証する。

- 最大長
- JSON 型
- 数値範囲
- 列挙値
- 文字列長
- コマンド頻度
- 重複
- 期限切れ

### 26.3 秘密情報

- `.env` をコミットしない。
- シリアル・ログへ秘密を出さない。
- AI へ API key や資格情報を貼らない。
- crash dump や CI log に含まれる可能性を確認する。

### 26.4 AI エージェントの権限

- 作業ディレクトリを限定する。
- 削除、外部送信、依存導入は確認可能にする。
- API 使用上限を設ける。
- 実行ログを保持する。
- 生成差分をレビューする。
- 出所不明の skill、rule、plugin を実行前に読む。
- 不可視 Unicode や外部から取得した命令を確認する。

安全クリティカルな角度制限、電流保護、通信断処理を LLM の実行時判断へ任せない。決定論的なコードと設定で実装する。

## 27. AI コーディングの実務

### 27.1 AI へ先に「調査だけ」を依頼する

新しい周辺機能では、最初の依頼を実装ではなく次にする。

- 仕様の要約
- 不明点
- 必要な一次資料
- GPIO／電源／通信上のリスク
- 最小検証手順
- テスト項目

不明点を解決してからコード生成へ進む。

### 27.2 良い依頼に含める情報

- 対象ボードと正確な部品型番
- 回路図と GPIO 表
- SDK、Rust、crate のバージョン
- 期待する振る舞い
- 禁止事項
- 受け入れ条件
- 既存設計との境界
- 変更可能なファイル
- 実行すべきテスト
- 実機確認が必要な項目

### 27.3 一 issue 一目的

例:

- LCD 単色表示
- JSON Lines parser
- タッチ raw 読み出し
- サーボ clamp

を別 issue にする。LCD、センサ、サーボ、通信を一つの生成依頼にしない。

### 27.4 AI レビューの使い分け

レビュー観点を分ける。

- 仕様適合
- 電気的前提
- エラー処理
- 並行処理
- メモリ
- セキュリティ
- 回帰
- テスト不足

複数 AI の指摘は候補であり、互いに一致しても一次資料と実機確認を省略しない。

### 27.5 回帰を防ぐ

- 正式仕様を一つにする。
- 決定ログを残す。
- 修正前にテストを書く。
- 変更を小さくする。
- 既存の校正・補正コードの意図をコメントとテストで固定する。
- AI に「既存の振る舞いを列挙してから変更する」と指示する。
- diff で意図外変更を確認する。

参照資料では、別の問題を修正した際に過去の基準電圧補正が消える回帰が起きた。テストと決定記録がない状態で、AI の全面書き換えを採用しない。

## 34. 完了の定義

DeskCat のマイコン側 MVP は、単に各部品が一度動いた時点では完了ではない。少なくとも次を満たした状態を完了とする。

- LCD が既定表情、happy、surprised を安定表示する
- タッチから一度の意味イベントを生成できる
- 軽い衝撃から一度の意味イベントを生成できる
- サーボが安全範囲と速度制限内で首を動かす
- サーボ動作中も ESP32 がブラウンアウトしない
- Pi と JSON Lines でコマンド、ACK、イベント、status を交換できる
- 不正入力、通信断、センサ切断から安全に復旧または縮退する
- 起動理由、fault、エラー・カウンタを取得できる
- クリーン環境からビルドと書き込みを再現できる
- PC テスト、実機テスト、MVP シナリオが記録付きで合格する
- GPIO、電源、プロトコル、安全制限の根拠資料が揃っている

この条件を満たして初めて、Pi 側の感情モデルや自律行動を安心して積み上げられる。
